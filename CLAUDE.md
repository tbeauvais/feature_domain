# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A prototype **feature-based application generator** (2014–2016). Users build a web page in the browser by dragging "Features" (Page, Text, Image, Container, Table, Form, Google Map, Swagger data resource, etc.) from a palette, editing their inputs, and watching the page regenerate live. The saved artifact is an **application model**: JSON listing feature instances and their inputs. The Ruby server is a thin CRUD/persistence layer. Nearly all the logic is client-side CoffeeScript on AngularJS 1.x. See `README.md` for the concepts (Feature, inputs, generate, application metadata) and `doc/AppArchitecture.jpg`.

## Project status

Dormant since Dec 2016 and **does not build on a current toolchain**. The goal is to modernize it. Findings from Oct 2026 (Ruby 3.3.6, macOS arm64):

- `Gemfile` pins `ruby '2.2.4'`, so `bundle install` refuses to run.
- With the pin removed, `Gemfile.lock` still fails: native gems puma 2.11, eventmachine 1.0.7, json 1.8.2 and libv8/therubyracer don't compile.
- With the lockfile also dropped (fresh resolve, therubyracer removed so ExecJS uses Node), gems install but the app **won't load**: `sinatra-assetpack` (abandoned, last release 2015) registers regex routes that Mustermann (Sinatra 2+) rejects (`regular expression should not contain ^`). **sinatra-assetpack is the main blocker.** It does CoffeeScript compilation, concatenation and minification, so replacing it means picking a new asset pipeline.
- No Redis server is installed locally. Specs use `fakeredis`, so Redis isn't needed for tests.
- Some specs probably fail even on the original stack: `spec/app_spec.rb` expects PUT to return 200 (app returns 204) and POST to echo the whole model (app returns only `{id}`).

**Dead external services** used by features and sample models: Yahoo YQL (`query.yahooapis.com`, shut down 2019), Google Image Charts (`chart.googleapis.com`, retired), IBM Bluemix (`*.mybluemix.net`), Watson TTS beta (`stream.watsonplatform.net`), keyless Google Static Maps. Expect those features to break at runtime.

**Vendored front-end libs** (committed in `app/js/vendor/`, not package-managed): jQuery 2.1.1, jQuery UI, AngularJS 1.3.13 (EOL), Bootstrap 3.2.0, d3 3.5.5, underscore, tree-model, plus angular drag-drop/sortable/colorpicker plugins.

## Modernization goals

The purpose of the project is to **showcase parametric, feature-based modeling** (in the spirit of CAD feature trees) applied to app generation. Preserve that model and don't swap in a generic page-builder library.

- **Frontend:** Vue 3 + TypeScript + Vite (Pinia for state), in `packages/web`. CoffeeScript and AngularJS 1.x will be removed.
- **Drag and drop:** Pragmatic drag and drop (Atlassian) for both the canvas and the feature tree. Gestures call pure engine edit operations (`insertFeature`, `moveFeature`, `removeFeature`, `canPlace`), so the logic is unit-tested and undo is a stack of models.
- **Engine:** keep the separation between generation and rendering. Features should be pure `generate(inputs, context)` functions that output a document tree plus metadata, and Vue renders that tree. No direct DOM mutation from features. Replace the retry loop with dependency-ordered (topological) regeneration.
- **Styling:** two separate concerns.
  - Editor UI uses Tailwind CSS + shadcn-vue (Reka UI), replacing Bootstrap 3, jQuery UI and the colorpicker plugin.
  - Generated pages do **not** use Tailwind classes. Tailwind only generates classes it finds at build time, and feature style inputs (colors, widths) are runtime parameters. Node components apply inputs as inline styles or CSS custom properties, with component-scoped CSS per node kind. Container layouts use CSS Grid.
  - A Theme feature exposes global style parameters as CSS variables on the page root.
  - The standalone preview renders without editor styles.
  - The model migration maps Bootstrap class values in inputs (`center-block`, `pull-left`) to plain values.
- **Backend:** Cloudflare Workers (Hono) serving the Vue build plus `/api/v1/models`. Storage is D1 (decided 2026-10-12; app data later goes behind a `RowStore` in the same database). The legacy `/api/app_features` endpoint is dropped. Persistence sits behind a small `ModelStore` interface (`list/get/create/update/delete`) so the backing store can change in one file.
- **Local dev:** local and Cloudflare must behave the same. The Worker runs in workerd (Cloudflare's runtime) with local D1, through the Cloudflare Vite plugin, and wrangler stores the data as SQLite files in `packages/worker/.wrangler/state/` (gitignored; `npm run db:reset -w packages/worker` resets it). Migrations and seeding are the same commands locally and remotely (`--remote`). No Docker or Redis: Cloudflare has no managed Redis, and a separate dev store would drift from production. Local data is seeded with the samples written for this app; models in browser storage are left alone, not imported.
- **Tests:** the engine is pure TypeScript, so its tests (Vitest) load `app_models/*.json` directly from disk as fixtures and need no storage layer.

### `packages/engine`: the parametric generation engine (pure TypeScript, no DOM, no platform globals)
- **v2 model** (`src/types.ts`): `{ version: 2, name, features: FeatureInstance[] }`.
  - Each instance has `feature`, `id`, `inputs` (plain values: strings, numbers, booleans, string lists) and, when placed, `placement: { parent, slot }`.
  - `parent` is the parent's **instance id**, or `$root` for the document. `slot` is a local key: `content` (root and Page), `r1c2` (Container cell), `body` (Panel). Renaming a feature never breaks placement.
  - References between features (e.g. Table -> DataResource) are `reference`-type inputs holding an instance id.
- **`migrate(legacy)`** (`src/migrate/`) is the only code that knows the legacy format. It converts it to v2 and returns `{ model, notes }`.
  - It maps legacy DOM-id targets (`#container_my_container_12_row_1_col_2`) to `{ parent, slot }` and resolves name-based data resource references to instance ids.
  - Values become **what the legacy app rendered**:
    - `disable` only counted when it was boolean `true`.
    - Other booleans used JS truthiness, so `"false"` meant on.
    - Containers with no valid rows or columns get the 1x2 default.
    - Bootstrap values (`text-center`, `pull-left`, `panel-success`) map to plain values.
  - Every interpretation is recorded as a note, and text using HTML is flagged. A legacy Text whose `{{DataResource.<Name>.<path>}}` bindings all read one data resource (named without spaces, as the legacy app did) gets that resource as its Data Resource and `{{path}}` values (a `mapped-input` note); any other `{{...}}` is left as written with a `data-binding` warning. Texts stored as v2 before values from data, with no Data Resource and legacy bindings, are mapped the same way on upgrade.
  - **Legacy looks are not carried over.** We don't match the old Bootstrap styling: newly ported features migrate content and placement only, and styling inputs (colors, sizes, Bootstrap style classes) are dropped with a `dropped-style` note so the feature takes our own defaults and the theme (`dropLegacyLooks`).
  - Unported feature types keep their scalar inputs and their legacy instance in `cache.legacy`. Every legacy type is now ported or dropped, so this is only for unknown types.
  - **Dropped feature types** (`DROPPED_FEATURES`): Watson Text to Speech (its IBM service is gone, and browsers and screen readers read pages aloud) and ScriptTest (it ran a script built from its inputs) are removed, from legacy models and from any v2 model holding them (e.g. stored while unported), with a `dropped-feature` note in the migration result (the editor applies migration on load but doesn't show its notes). They don't claim their instance id.
  - **v2 models are upgraded, not re-migrated:** any feature still carrying `cache.legacy` whose type now has an input migration is migrated from it, keeping its placement, with an `upgraded-feature` note. Features saved before one of their inputs changed shape are upgraded by `INPUT_UPGRADES` (each returns undefined when the instance is current): Pages drop legacy colors; Headers' Bootstrap `text_style` / tone `background` become Color and Background; Panels drop `style`; Headers saved as `colour` (before US spelling) are renamed to `color` in place. Otherwise the same object is returned. The editor applies this on load and saves the result; the preview upgrades in memory only. So porting a feature also fixes models stored before it was ported.
- **`generate(model, registry?)`** (`src/generate.ts`) returns `{ root, metadata, graph, edgeKinds, referenceEdges, exports, order, diagnostics }` (`exports`: each generated feature's frozen exports, e.g. a resource's operations for the editor's pickers).
  - The graph has `placement` edges (parent -> child) and `reference` edges (referenced -> referencing).
  - Features generate in topological order. Siblings attach to their slot in **model order**.
  - Suppression (`disable`) and skipping propagate along both edge kinds. Only features that declare a `disable` input can be disabled; a stray stored `disable` (e.g. on a Theme or Data Resource) is ignored.
  - Never throws: unknown feature, missing or unresolved placement or reference, missing slot or node, invalid or duplicate node ids, cycles, out-of-order (a feature listed before something it depends on), and exceptions thrown by a feature's `generate`, `slots` or `dependencies` all become `diagnostics`.
  - `metadata.targets` lists only slots that were actually generated (valid drop targets).
  - Never mutates the model or feature output.
- **Feature API** (`src/feature.ts`): implement `FeatureDefinition`.
  - Declare `inputs` and `placement: 'required' | 'none'`. An input's `default` is what it means when a stored instance lacks it (`resolveInputs` fills it in), so adding an input never changes existing models; `initial` (optional) is the value for new instances when that differs (`createFeatureInstance` uses `initialInputs`). Example: Image's Source defaults to `link` (older images were links) but new Images start as `illustration`.
  - `group` puts an input under a section heading in the inspector (e.g. the Theme's Color, Typography, Shape and space, Components); ungrouped inputs come first.
  - `showWhen` shows an input in the inspector only while other inputs have given values (`isInputShown`): one condition or a list that must all hold. A condition is `{ input, equals }` (`equals` may list several values) or `{ input, notEquals }`, which also matches unrecognized values, so the inspector shows what generation falls back to.
  - A `reference` input with `soft: true` is a **soft reference**: if the target is missing, the wrong type, suppressed or not generated, the feature still generates (with a warning) and `ctx.resolve` returns undefined, so it can fall back. Soft edges still order generation, but cycle detection ignores them, so a cycle that only closes through a soft reference skips nothing. Diagnostics about a soft target are reported only when the referencing feature actually generates.
  - Optionally declare `slots(inputs)` (slot keys; mark the matching nodes with `slot`) and `dependencies(inputs)` (ids beyond `reference` inputs).
  - `generate(inputs, ctx)` returns `{ node?, exports? }`.
  - The context provides `ctx.nodeId(part?)` for node ids (`12`, `12.r1c2`; the engine rejects ids a feature doesn't own), `ctx.resolve(id)` (only declared dependencies; returns a deep-frozen copy of their `exports`) and `ctx.report(severity, message)`.
- **Editor mode:** `generate(model, registry, { placeholders: true })` adds `placeholder` nodes where placed features produced nothing (unknown types, or skipped by a problem), so the editor can show and select them. Suppressed features get none. `metadata.features` lists unknown features too, with status `unknown`, and every non-generated feature has a `reason`: the first problem found, not later effects. The tree, placeholders and inspector all use it.
- **Edit operations** (`src/edit.ts`): `addFeature`, `insertFeature`, `moveFeature`, `removeFeature` (removes the subtree, clears reference inputs that pointed into it, and reports those broken references), `updateInputs`, `canPlace` (the slot must be generated, the feature placeable, and not inside itself) and `nextInstanceId`. Each returns a new model and is pure. `insertFeature` and `moveFeature` validate targets with `canPlace` (throwing `EditError`). After each edit, `normalizeOrder` keeps dependencies first *without changing the page*: siblings in a slot keep their order, so dependencies are pulled forward. A model whose ids repeat is left as it is (reordering could change which copy the page shows). Edits therefore never cause `out-of-order`. A seeded randomized test applies hundreds of random edits, and checks the invariants plus that normalizing any shuffled model leaves the rendered page identical.
- **Edit marks** (`src/text-edit.ts`): text a node shows as a plain copy of an input carries `edit: { <prop>: EditMark }` (via `node(…, { edit })`, or the `input` argument of `title()` / `paragraphs()`), so the editor can edit it in place. An `EditMark` is `{ input, kind: 'text' }` (the whole input), `{ kind: 'paragraph', index }` (one non-empty paragraph of a text split on blank lines) or `{ kind: 'item', entries }` (a list node's items, item i being entry `entries[i]`; lists that leave out empty entries skip them). Derived text carries none (a Text filled in from data, a Weather card's fallback title). Generation skips a feature whose marks name an input it doesn't declare or that doesn't fit (`invalid-edit-mark`). `markLocation` / `findEditable` map between marks and a `TextLocation` (feature, input, entry); `editText` writes typed text back (trimmed, non-breaking spaces made plain; emptying an entry or paragraph removes it; a paragraph stays one, blank lines in it becoming line breaks; text the page already shows changes nothing) and `insertTextAfter` adds the next entry or paragraph. The contract tests check every feature's marks and that edits round-trip. Marked so far: Header, Panel heading, List items, List card, Text, Text with title, Image with text, Link, Button, Map title and address, Weather title.
- **Higher-level features compose primitive nodes.** Don't add a one-off node kind for a feature: build its output from the shared primitives (`heading`, `paragraph`, `image`, `list`, …) and layout nodes (`stack`, `media`, `card`), using the helpers in `features/blocks.ts` (`title`, `paragraphs`). Child node ids come from `ctx.nodeId(part)`. Styling and safety rules then live in one place. (User-built composite features are a planned phase.)
- **Node kinds** are typed: `NodeKinds` in `src/types.ts` maps each `kind` to its props. Extend it with declaration merging.
- **Features** live in `src/features/`, one file each, registered in `src/features/index.ts`. Ported so far: Theme, Page (colors come from the theme; the migration drops legacy `border_color` / `background_color` with a `dropped-style` note), Container, Panel (Emphasis: normal, highlight, quiet; the migration drops the Bootstrap style), Text (a paragraph of its own; with a Data Resource (a soft reference) and optional Operation, under "Values from data", its `{{path}}` values are read from that resource's whole answer at runtime, or its rows for sample data, e.g. `{{public_repos}}`, `{{length}}`, `{{0.name}}`, with an optional table filter: `{{0.updated_at | date}}` (`VALUE_FILTERS`; an unknown one is a warning); the Text input's `hint` shows the syntax; `parseBindings` splits the text into literal runs and values, never evaluated; values without a Data Resource show as written, with a warning; the portfolio sample's profile line reads a GitHub profile), Header (Color: ink, accent, muted; Background: none, tint, band. The migration maps Bootstrap tones: primary and info to accent, muted to muted, success / warning / danger to accent with a `mapped-style` note, any background tone to tint), Image (Source: a built-in illustration or a link), List, Separator (Style: line, or a wave / dots / ruler divider illustration), Link, Button (our own styles: primary, secondary, soft, link; links and buttons render only http(s) addresses), Text with title and Image with text (legacy TextWithParagraph / ImageWithParagraph: a title over paragraphs split on blank lines, with an optional image), List card (legacy ListGroup: its comma list becomes items, and the last item, which the legacy app showed large, becomes the highlight), Map (legacy GoogleMap, same type id, whose keyless Google Static Maps image is dead: a card with a Title, our `banner/map` street-map drawing (decorative, the same for every address) at a Height (`MAP_HEIGHTS`: short 3:1, medium 2:1 like the legacy 400 × 200, tall 4:3), the Address, and an "Open in Google Maps" link (`googleMapsUrl`, a keyless Maps URL search for the address; ### `packages/worker`: the Cloudflare Worker (Hono, D1)
- **What it serves.** `wrangler.jsonc` (Worker name `app`, so its address is `app.feature-domain.workers.dev`; its Vite environment is `app`). Static assets are the web build: unknown paths get `index.html` (client routes like `/models/:id`), and `html_handling: none` serves files at their own paths (`/preview.html`, no redirect). Only `/api/*` runs the Worker (`run_worker_first`).
- **API** (`src/app.ts`, `createApp`): `/api/v1/models` list (`[{id, name}]`), POST (201 `{id}` + `Location`), and `/:id` GET, PUT (204), DELETE (204; deleting a missing model is not an error); other methods get a 405 with `Allow`. A model's revision is its `ETag` (`"3"`; POST, GET and PUT send it): GET answers a matching `If-None-Match` with a 304, PUT with `If-Match` saves only over that revision (a 412 carrying the stored revision's ETag otherwise; `*` means any; a weak `W/"3"` counts as 3, since Cloudflare's edge weakens tags when it compresses; anything else is a 400), and PUT without it overwrites. Model reads are `Cache-Control: no-cache`. A missing model is a 404 (the Ruby app's 410 is gone). Models are checked with the engine's `validateModel` (400 with `problems`), sent as `application/json` (else 415), at most `MAX_MODEL_BYTES` (413), counting both the body and the stored row (the JSON plus the name, stored twice). **Local D1 doesn't enforce Cloudflare's limits** (2,000,000-byte rows, 100,000-byte statements), so tests check sizes themselves. Every `/api` response is JSON; errors are `{ error, problems? }`, and a 500 reveals nothing.
- **Storage** (`src/d1ModelStore.ts`): `D1ModelStore` implements `ModelStore` on `migrations/` (`models(id, name, model, created_at, updated_at, revision)`, `settings(key, value)`; one `UPDATE … AND revision = ? RETURNING revision` checks and writes; `test/migrations.test.ts` checks each migration on rows stored before it, so no save lands in between); the JSON leaves out the model's id (the row's id is put back on read); `list()` orders by `created_at, rowid`. Schema changes are new migration files, applied by `npm run db:migrate` (`scripts/migrate.ts`; `-- --remote` for Cloudflare).
- **Seeding** (`scripts/seed.ts`, `npm run db:seed`, `-- --remote` for Cloudflare): SQL from `seedSql` stores the web app's samples (`SAMPLE_MODELS`, ids `sample-<set>-<n>`) unless the `samples-seeded` setting says it was done, so deleted samples don't come back; running it again changes nothing. Cloudflare runs the file statement by statement, so the setting is `seeding` until the last statement, and a seed that stopped partway stores only the missing samples when run again. It runs through `tsx --conditions=@feature-domain/source`. Scripts and tests run wrangler through `scripts/wrangler.ts` (this package's own copy, never `npx`).
- **Tests** (Vitest in Node): `test/localD1.ts` gives each file a fresh database migrated by wrangler and reached through workerd (`getPlatformProxy`), so the contract (`describeModelStore`), route and seed tests use real local D1. `e2e/api.spec.ts` in packages/web tests the built Worker. (`@cloudflare/vitest-pool-workers` needs Vitest 4, so it isn't used.)
- **Deploying** (`infrastructure/`, its README has the steps): a Cloudflare account of its own, on `app.feature-domain.workers.dev`. Terraform (state in R2) owns what outlives a deploy: the D1 database and Cloudflare Access (an email allow list; sign-in by one-time code or Cloudflare login) in front of the whole hostname, editor and `/api` alike; CI runs `terraform fmt -check` and `validate`. wrangler deploys the code: `npm run deploy -w packages/web` builds, migrates and seeds D1 with `--remote`, then `wrangler deploy` uploads the build's generated config, so Cloudflare runs what `vite preview` runs. Migrations run before the upload, so each must keep working with the Worker already running (add first; drop or rename in a later deploy). Preview URLs are off (Access doesn't cover them), and `test/config.test.ts` checks the Worker's name matches the hostname Access protects and the Vite environment configured for it. The Access application and policy are protected from destroy, like the database. Credentials live in `~/.config/feature-domain/cloudflare.env`, never in the repo.
- **Versions.** `wrangler` is pinned exactly to the version `@cloudflare/vite-plugin` depends on, so dev, tests and preview share one wrangler, miniflare and workerd. Upgrade them together.

### `packages/web`: the Vue app (Vite, Vue 3, Pinia, vue-router, Tailwind v4)
- **The Worker in Vite.** `vite.config.ts` loads the Cloudflare Vite plugin with `packages/worker/wrangler.jsonc` (left out under Vitest), so `vite dev` and `vite preview` serve `/api` from the Worker in workerd, and `vite build` emits `dist/client` (the app) and `dist/app` (the Worker and its generated `wrangler.json`). The two-page input is set on the `client` environment only, and the Worker's environment gets the `@feature-domain/source` condition too. Its D1 data is the worker package's; `FD_STATE_DIR` points elsewhere (the e2e tests use a fresh `.wrangler/e2e-state`).
- **Two pages.** `index.html` (`src/main.ts`) is the editor and uses Tailwind. `preview.html` (`src/preview.ts`) shows only the generated page and has no Tailwind, so it looks like a published site.
- **Rendering.** `src/renderer/` renders a `DocNode` tree. `NodeView` picks a component per node kind from `nodeComponents.ts`, which is typed as a full `Record<NodeKind, Component>`, so a new kind fails the typecheck until it has a component.
- **Model ids in the DOM.** `NodeView` adds `data-node-id`, `data-feature-id`, and on slots `data-slot` / `data-slot-parent`, so selection and drag-drop can map the DOM back to the model.
- **Generated-page styling.** `document.css` is plain CSS driven by the theme. The legacy Bootstrap look is gone.
  - **Themes** (`packages/engine/src/theme/`): `deriveTokens(params)` turns theme settings (accent, band color, light/dark scheme, font pairing, base size, scale ratio, radius, density, shadow) into `--fd-*` custom properties. Colors are computed in OKLCH with gamut mapping, and `ensureContrast` moves each text color's lightness until it reaches 4.5:1 against every surface it can sit on. It also derives six chart colors (`--fd-chart-<n>`, `CHART_COLORS`): the accent, then hues a sixth of a turn apart ordered so neighbors are a third apart, alternating lighter and darker, each at least 3:1 against the page and cards; and a band set (`--fd-band-chart-<n>`, 3:1 against the band and its raised cards), which a band well re-points `--fd-chart-<n>` to. Seeded property tests cover contrast, lightness order, badge hue separation, chart colors and determinism. `clampThemeParams` turns any stored values into valid settings.
  - **Component styles** (`panel`, `table`, `well`) are separate named looks. The element carrying a theme (`[data-fd-scheme]`: the root now, pages later) provides it (`renderer/theme.ts`, provide/inject), and each component puts its choice on its **own** element as `data-fd-<component>`, so a nested theme wins over an outer one. `document.css` has one rule block per option, keyed to the component's own attribute (never an ancestor's). `deriveTokens` also returns `adjustments`: colors it changed for readability, in words, for the editor to show. A web test fails if any option lacks rules, if `document.css` uses a `var(--fd-*)` the engine doesn't emit, or if a font pairing names a web font that isn't bundled. A `band` well re-points the color tokens to the band set, so content inside stays readable.
  - **Built-in themes** (`THEME_PRESETS`): Warm Editorial (`DEFAULT_THEME`) and Night Garden (`NIGHT_GARDEN`: dark, forest accent and band, small corners, compact, flat, 1.2 scale, 15px). A built-in theme is only a set of settings; tests check each derives with no readability adjustments. `themeInputs(params)` / `themeParams(inputs)` convert between settings and a Theme's inputs, and `matchingPreset(inputs)` names the built-in theme a Theme matches exactly.
  - **Theme feature** (`features/theme.ts`, `placement: 'none'`, no `disable`): its inputs are the theme settings, clamped; it exports `{ params, tokens }` and reports readability adjustments as info. A Page's `theme` input is a **soft reference** to it: the page carries the tokens as `props.theme`, and `PageNode` applies them and provides the theme to the components inside. A page without a theme (or with a missing one) inherits the theme around it. `RootNode` takes the first page's theme, else `DEFAULT_THEME` (Warm Editorial: Newsreader display, Geist body, Geist Mono labels, warm cream, vermilion accent). Pages are full width (side padding keeps content within 1120px), so a themed page paints edge to edge.
  - Adding a Theme from the palette also points every page without a working theme at it (`useThemeOnUnthemedPages`), in the same undo step.
  - **Fonts are self-hosted** via `@fontsource-variable/*` packages (OFL), imported in `DocumentView.vue`. Never load fonts from a CDN: `e2e/network.ts` blocks every non-localhost request and fails the test if a blocked one was a stylesheet, font or script.
  - `.fd-root` is a hard boundary. The root starts from `all: initial`, so nothing is inherited from the editor page, and everything inside is reverted to browser defaults (`all: revert`). Then `document.css` applies its own styles.
  - **Except shapes inside an `<svg>`:** their geometry and paint (`r`, `d`, `fill`, …) are CSS properties set by presentation attributes, so a revert would erase the drawing. `:where(.fd-root *:not(svg *))` gets `all: revert`; SVG internals revert only the box properties editor base styles set on every element (border, outline, box-sizing, margin, padding). The e2e isolation test catches anything else that leaks.
  - **Illustrations** (`renderer/illustrations/`, one SVG component each, mapped in `index.ts` as a full `Record<IllustrationId, Component>`) are our own inline SVG. Every color is an inline `style="fill: var(--fd-…)"` (presentation attributes can't hold `var()`) or `currentColor` (dividers, so the Separator's color applies); pattern ids come from `useId()`. Banners are two stacked SVGs, so they suit any height: a background that fills the frame (`slice`) and a drawing that always fits whole (`meet`). Tests check each has no scripts, handlers or external references, uses only tokens the engine emits, and hard-codes no colors. Never load illustration images from other sites.
  - An e2e test renders the preview's document at exactly the editor canvas's width, then compares *every* computed property of every element in the editor and the preview, except a short list of layout-dependent ones, including with leaky utility classes added to the canvas wrapper. It fails if the isolation breaks.
  - **Tailwind utilities have no effect inside `.fd-root`.** Editor overlays (selection outlines, drop indicators, inline editors) must live outside it, positioned from bounding boxes, or use plain CSS.
  - Containers and card panels with nothing in them (e.g. holding only disabled features or ones of an unknown type) add no margin or empty card (`:empty` / `:has`); in the editor their slots still get drop areas, and empty containers keep their margin (`main.css`).
  - Text is always plain text, never `v-html`. Responsive images get no fixed height (their height follows the width, like Bootstrap's `img-responsive`). URL policies are in `renderer/urls.ts`: links and data fetches are http(s) only; image sources are http(s), relative or `data:image/`.
- **Runtime data** (`renderer/data.ts`): each document has one `DataStore` (provided by `DocumentView`, given the model id). Readers of the same address share one fetch (`FETCH_JSON`, injectable; phase 3 routes it via `/api/proxy`): tables and charts read rows (`rows(source)`, each taking its own `path`; `reload(source)` refreshes them all), and a Text's values read a source's whole answer (`answer(source)`: the JSON at its address, or sample rows with added ones; it registers as a reader of the resource, so a Form's send reloads it too; "…" while loading; a value the answer doesn't have, or that couldn't be loaded, shows "—" on the page and its marked `{{binding}}` on the editor canvas, whose title says which (`store.live` tells them apart); an empty value shows empty; screen readers hear words instead of the marks), and a Weather card reads the whole response (`json(endPoint)`, as a `FetchState`, parsed by `renderer/weather.ts`; `refetch(endPoint)` for Try again). A stale response is discarded. A failed address is tried again when a new reader arrives, and an address with no readers left is dropped (so typing a URL keeps nothing). A source with `rows` (sample data) fetches nothing: it shows its rows plus rows added since (by a Form; capped at `MAX_SAMPLE_ROWS`), kept per model in `localStorage` (`feature-domain:sample-rows:<model id>`, ignored if unreadable, forgotten when the model is deleted). `send(action, values, fields)` (a Form) and `delete(action, row)` (a table row) change data: on sample data they add or remove added rows (an added row without an id gets the next one after the sample's, as a server would: `sampleIds` on the action, text or number like the sample's; the last id given is stored too, so a deleted row's id is never reused); otherwise they go through `SEND_REQUEST` (injectable, http(s) only), path fields filling `{name}` placeholders (`fillPath`, which refuses `.` and `..`), query fields added, the rest as the body, then `reloadResource` refetches every address that resource is read through. `follow()` picks up rows added in another tab (the preview follows the editor). On the editor canvas (`DocumentView`'s `editing`, so the store isn't `live`) forms and row deletes change sample data but never send to an address: they throw `NotSentFromEditor`, which says to open the preview. Table fields read a key the row has as a whole (e.g. `first.name`) before reading it as a dotted path.
- **Charts** (`nodes/ChartNode.vue`, Chart.js bundled from npm, only the controllers used are registered; loaded lazily with `defineAsyncComponent`, so only pages with a chart download its roughly 65 KB gzipped): drawn on a canvas with animation off, after `document.fonts.ready`, in colors and fonts read from the theme tokens around it, and redrawn only when what it draws changes: a signature of points, type, height and theme values (generation makes new objects on every edit), updating the chart in place when only the points change; any chart Chart.js still holds on the canvas is destroyed first. Points come from `renderer/chartData.ts` (guessed fields, passing over id-like keys and long text, plain-decimal numbers only, at most `MAX_CHART_POINTS`), and rows left out are counted in a note. The canvas has an `aria-label`, and the numbers sit in a visually hidden table (hidden by a wrapping div: `overflow` doesn't clip a table box, which would stretch the page). Loading, error with Try again, and empty states as tables.
- Table row delete: a Delete button per row (on sample data only rows a form added, the column only once there are some; on an address always, so it stays while rows reload), asked inline ("Delete this row?" Delete / Keep), never a browser dialog. Keyboard focus follows: to the question's Delete, back after Keep, to the next row's Delete (else the table) after deleting.
- A card Panel holding only tables, charts or forms (placeholders aside) lets them be the cards, in the editor as in the preview.
- **Forms** (`nodes/FormNode.vue`): labeled fields with hints, required and number checks before sending (and never sent with every field empty), sending / sent (a live status) / failed (an alert naming the site) states, fields cleared after sending.
- **Tables.** Tables read rows through the data store (`useTableRows` in `renderer/rows.ts`, with `reload` for Try again). Cells use a small filter language (`renderer/filters.ts`: `uppercase`, `lowercase`, `date`, `number` (every decimal, or `number :2` for fixed places; text must be a plain decimal and keeps every digit), `currency` (US dollars, or `currency :EUR`; same number rules), `badge`, `dataLink :path`); paths read only a row's own keys, and links are only ever http(s).
  - A table is a card: an optional Title with the row count (else the count in a footer), labels in the body font on a tinted band that is sticky while rows scroll ("Scroll after (rows)": stored tables without it show every row, new ones scroll after 10; the scroll box is a focusable, named region only while it actually overflows, measured with a ResizeObserver), dense rows with a hover highlight, stripes only for the theme's `striped` style.
  - Figures (`number` / `date` filters, or columns whose loaded values are all numbers) are right-aligned with tabular digits. Badges take the theme's four badge tints (`--fd-badge-<n>`, hues a quarter-turn apart from the accent, contrast-checked), given out per column in order of first appearance.
  - Loading shows skeleton rows under the real header; empty shows the `spot/empty` illustration; an error names the host and offers Try again.
  - A card Panel holding only a table lets the table be the card (`:has`). At phone width (`@container`, 520px) rows become cards with label/value pairs and no inner scroll box.
- **Editor** (`src/editor/`, `views/ModelView.vue`): a full-height shell. A top bar (logo link, model name, save state, undo/redo, `?` shortcuts dialog, Preview, delete), three columns, and a status bar (problem and feature counts; its button opens the model-wide Problems panel). Below `lg` the columns stack.
  - **Left: palette and feature tree.** The palette is grouped (`editor/palette.ts`; types it doesn't list go under "More") with inline SVG icons (`FeatureIcon.vue`). The palette folds away (remembered per browser via `editor/prefs.ts`; folded tiles stay in the DOM so drag and drop keeps them). Tree rows collapse (`editor/treeCollapse.ts`, reset when another model loads; selecting something inside opens its rows), pages show the theme they use, and Theme rows show an accent swatch. The palette adds a feature into the selected feature's first slot, else after the selection, else on the first page (`editor/targets.ts`). The tree is built from generation metadata (`editor/featureTree.ts`), not the DOM, so skipped, unknown and suppressed features appear with their reasons. Features that are never placed (data resources, themes) go under "Resources and themes"; placeable features whose placement is missing or broken go under "Not on the page".
  - **Empty states:** a page the model puts nothing on gets a hint with quick-add buttons (`EmptyPageHint.vue`, outside `.fd-root` like the selection outline; a page holding only disabled features gets none). The hint is removed entirely during a drag, so drops reach the page, and otherwise only its buttons take the pointer; the tree says when nothing is on the page, the Problems panel when there are none, and the model list explains models when there are none.
  - **Center: the canvas.** A toolbar switches the canvas between Desktop (fills the space), Tablet (820px) and Phone (390px) widths; Tablet and Phone are fixed, so the canvas scrolls sideways in a small window (`editor/canvasWidth.ts`, remembered per browser). Generated pages size themselves from the document's own width (`.fd-root` is a CSS container; `cqi` units and `@container` rules, never `vw` or `@media`), so the narrow canvas shows exactly what a phone would. Clicking selects the nearest `[data-feature-id]`, and links don't navigate. `SelectionOverlay` outlines the selection from outside `.fd-root`.
  - **Right: the schema-driven inspector** (`InputField` picks a control from each `InputDef`), a Location select limited to slots `canPlace` allows, delete (subtree, after a confirmation listing what goes), and the problem list.
    - Inputs sit under their `group` heading, sections in the order the feature declares them (`editor/sections.ts`).
    - A Theme gets **Start from** (`ThemePresets.vue`: a swatch per built-in theme; picking one sets every setting in one undo step, `applyThemePreset`, and a theme still named after a built-in theme takes the new name; picking the one it already is changes nothing). `matchingPreset` marks none while a stored value is invalid.
    - Any feature something references shows **Used by** (`usedBy(result, id)` in the engine reads `result.referenceEdges`, which also holds references from a feature placed in the one it references; model order; e.g. a Theme's pages, a data resource's tables). Clicking one selects it, and disabled or skipped ones are labeled. An unused Theme offers "Use on all pages without a theme".
    - With nothing selected it summarizes the model (counting what is on a page, as the tree does) and offers "Add a theme" when there is none.
  - **Inputs.** List and number fields keep a local draft while typing. Normalized values (trimmed lines, parsed numbers) go to the model, but they don't overwrite the field until blur. Selects show a disabled "Missing: …" option for values that no longer exist. Operation inputs (`control: 'operation-select'`, with the HTTP `methods` that fit) are selects of the referenced resource's operations, from `result.exports`. The API spec's stored spec uses `control: 'api-spec'` (`ApiSpecField.vue`: summary, Load spec, paste box). The Weather's Place uses `control: 'place-search'` (`PlaceSearchField.vue`: Find lists Open-Meteo's places, `editor/places.ts`; picking one sets the place and its coordinates as one undo step through `InputField`'s `changeInputs`, and focus stays in the field). An input's `hint` is a line of help shown under it (and named by `aria-describedby`). Inputs with `commitOnBlur` (the coordinates) apply typed text when the field is left or Enter is pressed, not per keystroke, because each value costs a request. JSON inputs (sample rows) use `control: 'json-area'` (a tall monospace text area). Inputs whose options are drawn as buttons use `control: 'segmented'` or `'illustration-gallery'` (`IllustrationGallery.vue`: the real drawings, painted with the theme of the page the feature is on, from `editor/themeFor.ts`); they are labeled as a group.
  - **Inline text editing** (`editor/useInlineEdit.ts`): node components put `data-edit-node` / `data-edit` / `data-edit-item` on text the engine marks, on the editor canvas only (`useEditAttrs`, from `DocumentView`'s `editing`), so the preview has no editing. A double-click, or Enter on a selected feature (its first marked text; from the page, nothing focused, or its tree row), makes the element `contenteditable="plaintext-only"` (browsers without it get a plain-text paste handler). The Enter confirming an input method's candidate is ignored. Enter or leaving commits through `store.editText` as one undo step; in a list or paragraphs Enter also adds `NEW_TEXT` after it and edits that (Shift+Enter only commits), and Escape on such an added entry takes it back out (`store.retract`, no redo step). Escape cancels. Before committing, the element's own rendered nodes are put back, so Vue re-renders it normally; any other regeneration ends the edit first (a pre-flush watch), and an edit that starts right after a change waits for the re-render. While editing, the feature isn't draggable (its and its ancestors' `draggable` are turned off, and `canDrag` checks `inlineEdit`), and the selection outline (amber) marks the edited text. Empty marked text shows an editor-only hint (`main.css`).
  - **Editing.** All edits go through `useDocumentStore` (`add`, `setInputs`, `editText`, `moveTo`, `remove`, `rename`), which applies pure engine operations, regenerates with placeholders, and autosaves 400 ms after the last change. **Saves go one at a time**, each sent with the revision the last one returned (`If-Match`), so a save is refused only when someone else saved in between, never by an earlier save from here; one ending after another model opened, or after `discard()`, is ignored. A refused save holds every later one (`saveState` `conflict`, or `deleted` for a 404) until the user picks **Load their version** (`loadTheirs`, which drops the edits and undo history) or **Keep mine** (`keepMine`, saving over the revision the 412 named), or **Save as a new model** (`saveCopy`); a failed save offers **Try again** (`retry`). The banner sits under the top bar (`save-problem`). On page hide the pending save goes out with `keepalive` (bodies under `KEEPALIVE_MAX_BYTES`, as browsers cap them at 64 KiB); `beforeunload` asks only when edits would be lost (`unsavedOnLeave`: a failed or held save, one queued behind another, or one too large for keepalive). Leaving within the app after a failed save asks before dropping the changes. **Saves made elsewhere** reach an open model through `useModelUpdates` (`stores/modelUpdates.ts`): this browser's other tabs hear of each save at once (`announceSaved` on a `BroadcastChannel`, `stores/modelChannel.ts`; messages carry a per-tab id, since every channel object in the saving tab hears them too), and every tab checks when shown again and every `CHECK_INTERVAL_MS` (10 s) while visible. Each check is a plain `get`: the browser revalidates its cached copy with the ETag, so an unchanged model costs a 304 (Playwright's routing turns the HTTP cache off, so e2e tests check the 304s at the API level). `refresh()` replaces the model only for a newer revision (a slow read can return an older one than a save that landed meanwhile) while nothing here is waiting to be saved and no text is being typed in place (the editor passes `inlineEdit`), ends undo history there, and shows a model deleted elsewhere as missing. Requests time out after `REQUEST_TIMEOUT_MS`, so a hung save becomes a failed one. An expired Access session gets its own banner: Sign in again (a new tab renews the session) and Try again, since reloading would lose the edits. When only the automatic upgrade on load is refused (another tab saved first), the editor quietly shows the stored model instead of a conflict. The editor and the preview both use it.
- **Drag-and-drop** (Pragmatic drag and drop):
  - `editor/dnd.ts` is pure and unit-tested. A drop zone is either an empty slot (append) or a feature (before, after, or "combine" = into its first slot). `evaluateDrop` maps the zone to a `PlacementTarget` and checks it with the engine's `canPlace`, detecting drops that change nothing.
  - `editor/useEditorDnd.ts` registers draggables and drop targets on the canvas (`[data-feature-id]`, `[data-slot]`), the tree (`[data-tree-id]`) and the palette (`[data-palette-type]`), rebuilding them after each regeneration and whenever collapsing or expanding re-creates tree rows (it watches `collapsedRows`). Anything else that re-creates draggable elements without a regeneration must trigger a re-registration too. It has one monitor that applies drops through the store (`moveTo` / `addAt`), so drops are validated and undoable.
  - Drop feedback lives in `editor/dndState.ts`, drawn by `DropIndicator` (canvas overlay, outside `.fd-root`) and `TreeRow`.
  - **Gotcha:** Chrome gives `[draggable]` elements `-webkit-user-drag: element; user-select: none` as presentational hints, which `all: revert` discards. `document.css` restores them inside `.fd-root`, or no drag ever starts.
  - Empty slots get a drop area in the editor only (`main.css`, `.fd-editor-canvas`).
  - Draggability is decided by feature type, so unplaced features can be dragged from the tree onto the page.
  - Before or after a Page (the document root) is offered only when dragging a Page; anything else dropped at a page's edge goes into it.
  - Links and images inside a feature are extra drag handles for that feature. A press in a form field or button never starts a feature drag (`canDrag`), and form fields keep mouse text selection (`document.css`).
- **Undo/redo.** The store records history at its single `apply()` point, with the selection. Consecutive edits of the same input (or the model name) within 1 s are one step, capped at 100 steps. Loading and the automatic upgrade are not undoable. Buttons, plus ⌘Z / ⇧⌘Z / Ctrl+Y, except in text-entry fields (selects and checkboxes do use them) and while a confirmation dialog is open. Deleting a model discards any pending save first (`store.discard()`). The inspector's Move up / Move down and Location select are the keyboard alternatives to dragging.
- **UI components.** These are shadcn-vue components (Reka UI) in `src/components/ui/`. They're added with `npx shadcn-vue@latest add <name>` from `packages/web`. The CLI is deliberately not a dependency (it pulled in vulnerable packages); its Tailwind variants are vendored in `src/styles/shadcn.css`. **After `add`, check `src/main.css` and `package.json`:** the CLI re-inserts a Google Fonts `@import` and icon packages. The editor must load nothing from other sites, and an e2e test enforces that. Confirmations use `confirmAction()` with `<ConfirmHost>` (an in-page AlertDialog), never the browser's blocking `confirm()`.
- **Validation at the boundary.** `ApiModelStore` refuses any answer that isn't what the API sends, and `useDocumentStore.load` checks every model with the engine's `validateModel` and catches any exception from `generate`. Bad data shows an error, never a blank page.
- **Storage.** Models live in the Worker's D1 database, reached through `ApiModelStore` (`src/stores/apiModelStore.ts`, a `ModelStore` over `/api/v1/models`; `src/services.ts` gives it to the app, tests swap in a `MemoryModelStore` with `setModelStore`). It reads revisions from ETags, weak ones too (`revisionOf`: Cloudflare's edge weakens them when it compresses), maps a 412 to `ModelConflictError` and a 404 on save to `ModelNotFoundError`, and never follows redirects: an expired Cloudflare Access session (a redirect, or an HTML page) is a `SignedOutError` asking to reload. Its contract tests run against the Worker's real routes in-process (`test/workerApp.ts`, which imports the Worker's app through a computed path so the web typecheck doesn't follow it into code typed for Cloudflare's runtime). The model list shows load and create errors. Models once kept in browser storage (before the Worker) are left there, not imported.
  - **The samples** (`SAMPLE_SET` 2) are written for this app as v2 models in `src/data/sampleModels/` (one file each, built with `sample()` in `build.ts`, so ids run 1, 2, 3… in dependency order): Start here (a short guide), Harbor Coffee (a café: hours, a Map, Weather), Ledgerly pricing (plan cards), Northwind sales (an API spec on sample data feeding a table, a chart, a form and a count), Tom Beauvais · projects (live GitHub data) and Shoreline JS meetup (a schedule, a signup form and a live count). They read like real pages: no placeholder text, our own banners (decorative) and drawings rather than photos from other sites, distinct button words, and links only to real sites for real things (the fictional businesses link to example.com); Start here uses the default theme, Northwind sales the built-in Night Garden, and the others themes of their own. Tests check they generate with no problems at all. The Worker's seed stores them (`npm run db:seed`). The legacy samples (set 1, migrated from `app_models/` and `sample.json`) stay as the engine's migration fixtures.
- **Engine imports.** The app imports the engine's TypeScript source through the `@feature-domain/source` export condition: `customConditions` in tsconfig, and `resolve.conditions` in `vite.config.ts`, which keeps Vite's defaults (and on the Worker's environment).
- **Tests.** Vitest + Vue Test Utils (jsdom) in `test/`. Playwright in `e2e/` runs against a production build. Tests run in parallel, so each gets a model API of its own (`e2e/storage.ts`, set up by `isolateNetwork`): the Worker's real routes in the test process over a `MemoryModelStore` seeded with the samples under the seed's ids (`sample-2-1` …); `store` puts a model there, `stored` / `changeStored` / `storedId` read and change it as another tab would, and `featureId` finds a sample's feature by name, so adding a feature to a sample doesn't break tests. `e2e/api.spec.ts` and `e2e/sync.spec.ts` (`isolateNetwork(…, { realModels: true })`: two tabs, other devices, conflicts, deletes, the save on the way out) use the real Worker and its D1. ## Architecture

### Server (Ruby/Sinatra)
- `config.ru` → `app.rb` (`App < Sinatra::Base`, modular style). `load_path.rb` puts `lib/` and the repo root on `$LOAD_PATH`.
- `app.rb` declares the asset bundles (sinatra-assetpack serves `app/js`, `app/css` and `app/images`, and compiles `.coffee` on the fly). **The JS bundle order matters**: vendor libs, then `application.js`, then `/js/*.js` alphabetically.
- Routes:
  - `GET /`, `GET /models/:id`: designer UI (`views/layout.slim` + `views/index.slim`, `designMode = true`).
  - `GET /models/:id/preview`: rendered app only (`views/content.slim`, no layout, `designMode = false`).
  - `/api/v1/models[/:id]`: REST CRUD on application models. GET on a missing id returns **410**, not 404. If the store is empty, `GET /api/v1/models` seeds it from `sample.json`.
  - `/api/app_features`: legacy endpoint that reads and overwrites `sample.json` on disk.
- `lib/model_access.rb`: models are stored as JSON strings in one Redis hash (`content_models`), keyed by UUID. The Redis client is created at class-load time (`Client` constant).
- `lib/redis_connection.rb`: reads credentials from `VCAP_SERVICES` (Cloud Foundry) with a fallback to `localhost:6379`.

### Client (CoffeeScript + AngularJS 1.3, `app/js/`)
- `application.coffee`: Angular module `sampleDomainApp`.
- `features.coffee` (~2000 lines, the core): `BaseFeature` plus ~20 `*Feature` classes, registered in the `FeatureClasses` map at the bottom. Each feature declares `name`, `icon`, an `inputs` schema (each input's `control` names a form directive in `form_directives.coffee`), optionally `visual_editor`, and a `generate(appMetadata, instance, inputs)` function. That function **mutates the DOM directly with jQuery** (appends into its target container) and returns `false` if its target doesn't exist yet. **To add a feature**: add a class and register it in `FeatureClasses`.
- `generator.coffee` (`AppGenerate`): runs every non-disabled feature instance in order and retries features that returned `false` (up to ~4 passes) so children can render after their containers. `generateInstance` does partial regeneration of one feature plus its dependents.
- `metadata.coffee` (`AppMetadata`): transient tree (tree-model.js) rebuilt on every generate. It records Pages → Targets, Features, DataResources (+ Operations), DataSchemas and feature dependencies. Features use it to discover each other, and editors use it to populate selectors (e.g. page targets, resources).
- `app_features.coffee` (`AppFeatures`): the loaded model's feature-instance list (add/move/delete/save via `$resource`).
- `controllers.coffee` (`ModelCtrl` load/save/saveAs/delete/preview, `FeaturesCtrl` drag-drop), `directives.coffee` (palette, feature list, editor, `generatedContent`, metadata view), `runtime.coffee` (`DataResource` service plus `serviceResource`/`googleChart` directives used by generated pages), `visual_editors.coffee` (inline contenteditable editing).
- Components communicate mostly through `$rootScope.$broadcast` events: `generateContent`, `featureSelected`, `featureUpdated`, `addFeature`, `moveFeature`, `postGenerate`, `deleteResource`, `postResource`.
- Generated HTML is `$compile`d by Angular after generation, so features can emit Angular directives in their markup.

### Data
- `sample.json`: seed feature list. `app_models/*.json`: example application models (Google Map, Swagger, "Buy Deal"; the Watson sample was removed when its feature was dropped). The new app no longer seeds these: they are the engine's migration fixtures.
- Feature instance shape: `{feature: "TextFeature", id: "27", inputs: {..., page_location: {name, target}}, cache: {}}`. `page_location.target` is a CSS selector (`#content_section`, `#page_container`, or a container cell id), which is how nesting works.

## Gotchas
- Instance ids are stringified integers (`AppFeatures.nextIndex`). DOM ids are derived as `<name>_<id>`, lowercased, with spaces replaced by underscores (`BaseFeature.instanceId`).
- Several inputs misspell `default` as `defaut` (e.g. the `disable` input), so they default to `''`. Specs depend on that behavior.
- `ScriptTestFeature` `eval`s a script built from user input. Persisted models can contain Angular `$$hashKey` fields.
- `rake package:build` just zips `app/`.

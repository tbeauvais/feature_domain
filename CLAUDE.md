# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A prototype **feature-based application generator** (2014–2016). Users build a web page in the browser by dragging "Features" (Page, Text, Image, Container, Table, Form, Google Map, Swagger data resource, etc.) from a palette, editing their inputs, and watching the page regenerate live. The saved artifact is an **application model**: JSON listing feature instances and their inputs. The Ruby server is a thin CRUD/persistence layer. Nearly all the logic is client-side CoffeeScript on AngularJS 1.x. See `README.md` for the concepts (Feature, inputs, generate, application metadata) and `doc/AppArchitecture.jpg`.

## Project status

Dormant since Dec 2016 and **does not build on a current toolchain**. The goal is to modernize it. Findings from Oct 2026 (Ruby 3.3.6, macOS arm64):

- `Gemfile` pins `ruby '2.2.4'`, so `bundle install` refuses to run.
- With the pin removed, `Gemfile.lock` still fails: native gems puma 2.11, eventmachine 1.0.7, json 1.8.2 and libv8/therubyracer don't compile.
- With the lockfile also dropped (fresh resolve, therubyracer removed so ExecJS uses Node), gems install but the app **won't load**: `sinatra-assetpack` (abandoned, last release 2015) registers regex routes that Mustermann (Sinatra 2+) rejects (`regular expression should not contain ^`). **sinatra-assetpack is the main blocker.** It does CoffeeScript compilation, concatenation and minification, so replacing it means picking a new asset pipeline.
- No Redis server is installed locally. Specs use `fakeredis`, so Redis isn't needed for tests.
- Some specs probably fail even on the original stack: `spec/app_spec.rb` expects PUT to return 200 (app returns 204) and POST to echo the whole model (app returns only `{id}`).

**Dead external services** used by features and sample models: Yahoo YQL (`query.yahooapis.com`, shut down 2019), Google Image Charts (`chart.googleapis.com`, retired), IBM Bluemix (`*.mybluemix.net`), Watson TTS beta (`stream.watsonplatform.net`), keyless Google Static Maps. Expect those features to break at runtime.

**Vendored front-end libs** (committed in `app/js/vendor/`, not package-managed): jQuery 2.1.1, jQuery UI, AngularJS 1.3.13 (EOL), Bootstrap 3.2.0, d3 3.5.5, underscore, tree-model, plus angular drag-drop/sortable/colorpicker plugins.

## Modernization goals

The purpose of the project is to **showcase parametric, feature-based modeling** (in the spirit of CAD feature trees) applied to app generation. Preserve that model and don't swap in a generic page-builder library.

- **Frontend:** Vue 3 + TypeScript + Vite (Pinia for state), in `packages/web`. CoffeeScript and AngularJS 1.x will be removed.
- **Drag and drop:** Pragmatic drag and drop (Atlassian) for both the canvas and the feature tree. Gestures call pure engine edit operations (`insertFeature`, `moveFeature`, `removeFeature`, `canPlace`), so the logic is unit-tested and undo is a stack of models.
- **Engine:** keep the separation between generation and rendering. Features should be pure `generate(inputs, context)` functions that output a document tree plus metadata, and Vue renders that tree. No direct DOM mutation from features. Replace the retry loop with dependency-ordered (topological) regeneration.
- **Styling:** two separate concerns.
  - Editor UI uses Tailwind CSS + shadcn-vue (Reka UI), replacing Bootstrap 3, jQuery UI and the colorpicker plugin.
  - Generated pages do **not** use Tailwind classes. Tailwind only generates classes it finds at build time, and feature style inputs (colors, widths) are runtime parameters. Node components apply inputs as inline styles or CSS custom properties, with component-scoped CSS per node kind. Container layouts use CSS Grid.
  - A Theme feature exposes global style parameters as CSS variables on the page root.
  - The standalone preview renders without editor styles.
  - The model migration maps Bootstrap class values in inputs (`center-block`, `pull-left`) to plain values.
- **Backend:** Cloudflare Workers (Hono) serving the Vue build plus `/api/v1/models`. Storage is D1 (decided 2026-10-12; app data later goes behind a `RowStore` in the same database). The legacy `/api/app_features` endpoint is dropped. Persistence sits behind a small `ModelStore` interface (`list/get/create/update/delete`) so the backing store can change in one file.
- **Local dev:** local and Cloudflare must behave the same. The Worker runs in workerd (Cloudflare's runtime) with local D1, through the Cloudflare Vite plugin, and wrangler stores the data as SQLite files in `packages/worker/.wrangler/state/` (gitignored; `npm run db:reset -w packages/worker` resets it). Migrations and seeding are the same commands locally and remotely (`--remote`). No Docker or Redis: Cloudflare has no managed Redis, and a separate dev store would drift from production. Local data is seeded with the samples written for this app and the home model; models in browser storage are left alone, not imported.
- **Tests:** the engine is pure TypeScript, so its tests (Vitest) load `app_models/*.json` directly from disk as fixtures and need no storage layer.

### `packages/engine`: the parametric generation engine (pure TypeScript, no DOM, no platform globals)
- **v2 model** (`src/types.ts`): `{ version: 2, name, features: FeatureInstance[] }`.
  - Each instance has `feature`, `id`, `inputs` (plain values: strings, numbers, booleans, string lists) and, when placed, `placement: { parent, slot }`.
  - `parent` is the parent's **instance id**, or `$root` for the document. `slot` is a local key: `content` (root and Page), `r1c2` (Container cell), `body` (Panel). Renaming a feature never breaks placement.
  - References between features (e.g. Table -> DataResource) are `reference`-type inputs holding an instance id.
- **`migrate(legacy)`** (`src/migrate/`) is the only code that knows the legacy format. It converts it to v2 and returns `{ model, notes }`.
  - It maps legacy DOM-id targets (`#container_my_container_12_row_1_col_2`) to `{ parent, slot }` and resolves name-based data resource references to instance ids.
  - Values become **what the legacy app rendered**:
    - `disable` only counted when it was boolean `true`.
    - Other booleans used JS truthiness, so `"false"` meant on.
    - Containers with no valid rows or columns get the 1x2 default.
    - Bootstrap values (`text-center`, `pull-left`, `panel-success`) map to plain values.
  - Every interpretation is recorded as a note, and text using HTML is flagged. A legacy Text whose `{{DataResource.<Name>.<path>}}` bindings all read one data resource (named without spaces, as the legacy app did) gets that resource as its Data Resource and `{{path}}` values (a `mapped-input` note); any other `{{...}}` is left as written with a `data-binding` warning. Texts stored as v2 before values from data, with no Data Resource and legacy bindings, are mapped the same way on upgrade.
  - **Legacy looks are not carried over.** We don't match the old Bootstrap styling: newly ported features migrate content and placement only, and styling inputs (colors, sizes, Bootstrap style classes) are dropped with a `dropped-style` note so the feature takes our own defaults and the theme (`dropLegacyLooks`).
  - Unported feature types keep their scalar inputs and their legacy instance in `cache.legacy`. Every legacy type is now ported or dropped, so this is only for unknown types.
  - **Dropped feature types** (`DROPPED_FEATURES`): Watson Text to Speech (its IBM service is gone, and browsers and screen readers read pages aloud) and ScriptTest (it ran a script built from its inputs) are removed, from legacy models and from any v2 model holding them (e.g. stored while unported), with a `dropped-feature` note in the migration result (the editor applies migration on load but doesn't show its notes). They don't claim their instance id.
  - **v2 models are upgraded, not re-migrated:** any feature still carrying `cache.legacy` whose type now has an input migration is migrated from it, keeping its placement, with an `upgraded-feature` note. Features saved before one of their inputs changed shape are upgraded by `INPUT_UPGRADES` (each returns undefined when the instance is current): Pages drop legacy colors; Headers' Bootstrap `text_style` / tone `background` become Color and Background; Panels drop `style`; Headers saved as `colour` (before US spelling) are renamed to `color` in place. Otherwise the same object is returned. The editor applies this on load and saves the result; the preview upgrades in memory only. So porting a feature also fixes models stored before it was ported.
- **`generate(model, registry?)`** (`src/generate.ts`) returns `{ root, metadata, graph, edgeKinds, referenceEdges, exports, order, diagnostics }` (`exports`: each generated feature's frozen exports, e.g. a resource's operations for the editor's pickers).
  - The graph has `placement` edges (parent -> child) and `reference` edges (referenced -> referencing).
  - Features generate in topological order. Siblings attach to their slot in **model order**.
  - Suppression (`disable`) and skipping propagate along both edge kinds. Only features that declare a `disable` input can be disabled; a stray stored `disable` (e.g. on a Theme or Data Resource) is ignored.
  - Never throws: unknown feature, missing or unresolved placement or reference, missing slot or node, invalid or duplicate node ids, cycles, out-of-order (a feature listed before something it depends on), and exceptions thrown by a feature's `generate`, `slots` or `dependencies` all become `diagnostics`.
  - `metadata.targets` lists only slots that were actually generated (valid drop targets).
  - Never mutates the model or feature output.
- **Feature API** (`src/feature.ts`): implement `FeatureDefinition`.
  - Declare `inputs` and `placement: 'required' | 'none'`. `single: true` allows one per model: of several that would generate, the first in generation order does and the rest are skipped with a `duplicate-single` error (so the model can't be published). `requires(exports)` names another feature type it needs, given what it exported: when none of that type generates, it is a `missing-required-feature` error (the feature still generates); a Database table whose rules need someone signed in requires a Sign-in feature. An input's `default` is what it means when a stored instance lacks it (`resolveInputs` fills it in), so adding an input never changes existing models; `initial` (optional) is the value for new instances when that differs (`createFeatureInstance` uses `initialInputs`). Example: Image's Source defaults to `link` (older images were links) but new Images start as `illustration`.
  - `group` puts an input under a section heading in the inspector (e.g. the Theme's Color, Typography, Shape and space, Components); ungrouped inputs come first.
  - `showWhen` shows an input in the inspector only while other inputs have given values (`isInputShown`): one condition or a list that must all hold. A condition is `{ input, equals }` (`equals` may list several values) or `{ input, notEquals }`, which also matches unrecognized values, so the inspector shows what generation falls back to.
  - A `reference` input with `soft: true` is a **soft reference**: if the target is missing, the wrong type, suppressed or not generated, the feature still generates (with a warning) and `ctx.resolve` returns undefined, so it can fall back. Soft edges still order generation, but cycle detection ignores them, so a cycle that only closes through a soft reference skips nothing. Diagnostics about a soft target are reported only when the referencing feature actually generates.
  - Optionally declare `slots(inputs)` (slot keys; mark the matching nodes with `slot`) and `dependencies(inputs)` (ids beyond `reference` inputs).
  - `generate(inputs, ctx)` returns `{ node?, exports? }`.
  - The context provides `ctx.nodeId(part?)` for node ids (`12`, `12.r1c2`; the engine rejects ids a feature doesn't own), `ctx.resolve(id)` (only declared dependencies; returns a deep-frozen copy of their `exports`) and `ctx.report(severity, message)`.
- **Editor mode:** `generate(model, registry, { placeholders: true })` adds `placeholder` nodes where placed features produced nothing (unknown types, or skipped by a problem), so the editor can show and select them. Suppressed features get none. `metadata.features` lists unknown features too, with status `unknown`, and every non-generated feature has a `reason`: the first problem found, not later effects. The tree, placeholders and inspector all use it.
- **Edit operations** (`src/edit.ts`): `addFeature`, `insertFeature`, `moveFeature`, `removeFeature` (removes the subtree, clears reference inputs that pointed into it, and reports those broken references), `updateInputs`, `canPlace` (the slot must be generated, the feature placeable, and not inside itself) and `nextInstanceId` (one past the model's highest numeric id, or its `lastId`: the highest it ever gave out, which `addFeature` and `removeFeature` keep and the editor carries through undo, another tab's save and Load their version with `keepLastId`, and past `used` ids too (`addFeature`'s `usedIds`: a published app's, for models from before `lastId`), so a removed feature's id is never given out again, and a new Database table never gets a published app's rows for a removed one; `validateModel` takes it as a whole number), `featureName`. Each returns a new model and is pure. `insertFeature` and `moveFeature` validate targets with `canPlace` (throwing `EditError`). After each edit, `normalizeOrder` keeps dependencies first *without changing the page*: siblings in a slot keep their order, so dependencies are pulled forward. A model whose ids repeat is left as it is (reordering could change which copy the page shows). Edits therefore never cause `out-of-order`. A seeded randomized test applies hundreds of random edits, and checks the invariants plus that normalizing any shuffled model leaves the rendered page identical.
- **Edit marks** (`src/text-edit.ts`): text a node shows as a plain copy of an input carries `edit: { <prop>: EditMark }` (via `node(…, { edit })`, or the `input` argument of `title()` / `paragraphs()`), so the editor can edit it in place. An `EditMark` is `{ input, kind: 'text' }` (the whole input), `{ kind: 'paragraph', index }` (one non-empty paragraph of a text split on blank lines) or `{ kind: 'item', entries }` (a list node's items, item i being entry `entries[i]`; lists that leave out empty entries skip them). Derived text carries none (a Text filled in from data, a Weather card's fallback title). Generation skips a feature whose marks name an input it doesn't declare or that doesn't fit (`invalid-edit-mark`). `markLocation` / `findEditable` map between marks and a `TextLocation` (feature, input, entry); `editText` writes typed text back (trimmed, non-breaking spaces made plain; emptying an entry or paragraph removes it; a paragraph stays one, blank lines in it becoming line breaks; text the page already shows changes nothing) and `insertTextAfter` adds the next entry or paragraph. The contract tests check every feature's marks and that edits round-trip. Marked so far: Header, Panel heading, List items, List card, Text, Text with title, Image with text, Link, Button, Map title and address, Weather title, Account's sign-in button.
- **Higher-level features compose primitive nodes.** Don't add a one-off node kind for a feature (only an interactive control the primitives can't express gets one, such as `form`, `account` and `sign-in`): build its output from the shared primitives (`heading`, `paragraph`, `image`, `list`, …) and layout nodes (`stack`, `media`, `card`), using the helpers in `features/blocks.ts` (`title`, `paragraphs`). Child node ids come from `ctx.nodeId(part)`. Styling and safety rules then live in one place. (User-built composite features are a planned phase.)
- **Node kinds** are typed: `NodeKinds` in `src/types.ts` maps each `kind` to its props. Extend it with declaration merging.
- **Features** live in `src/features/`, one file each, registered in `src/features/index.ts`. - **Database tables** (`features/database-table.ts`, `src/tables.ts`, `src/rows.ts`; the Data Apps slice, iteration 1). A Database table (`placement: 'none'`, in `DATA_RESOURCE_TYPES`) is a data resource over rows the app keeps: its Fields input is a string list, one field per line (`title: text, required`, `status: choice open | done, default open`; types text, long text, number, date, choice, yes/no; an option or default holding a comma, `|` or a quote is double-quoted, `default "Paris, France"`; `parseField` / `formatField` round-trip, `tableSchema` reads the list with a problem per bad line), and its Sample rows are checked against the fields. It exports `DatabaseTableExports`: `GET rows`, `POST rows` (a parameter per field, with `enum`, `format`, `default`, required unless defaulted), `PATCH rows` and `DELETE rows` (named like sample data's operations), a `Row` / `Rows` schema (so Table gets columns, Form fields, Text and Chart rows with no change to them), and `table` (`key`: the instance id, `name`, `schema`, `sampleRows` as stored, `access`). **Access rules** (`src/access.ts`, the Data Apps slice, iteration 3): under "Who can", a rule per operation on the published app, `see_rows` (listing and reading), `add_rows`, `change_rows`, `delete_rows`: anyone, signed in, owner (only the person who added the row; not for adding) or nobody (`ROW_RULES`, `ADD_RULES`; `rulesFor(access, operation)`: a change or delete answers to the See rule too), defaulting to anyone so tables stored before rules work as they did; and `deleted_accounts`, what a deleted account's rows become: deleted (the default) or kept without their name. An unknown choice is an error and reads as nobody (never opened by a typo). Rules needing someone signed in without a generating Sign-in feature are an error (`requires`). They export as `TableAccess` (`OPEN_ACCESS` the defaults; `rowOperation(method)`, `needsPerson`, `accessNeedsSignIn`), enforced only by the Worker on live rows; the builder's draft rows never apply them. `created_by` is a `ROW_SYSTEM_FIELDS` name, so no field takes it. Addresses are **relative to the app**: `tables/<key>/rows[/{id}]` (`tableRowsAddress`; `isAppDataAddress` accepts only that form, a row by `{id}` or a row id (built on `isTableKey` and `isRowId`), and `isDataAddress` accepts it; the page's data store fetches it as `modelRowsAddress(model, address)`, `/api/v1/models/<its own model>/tables/…`, the only form of it `isModelRowsAddress` accepts; a published app's page fetches it as `appRowsAddress(address)`, `/api/v1/app/tables/…` (`APP_API_PATH`, on the app's own host; `isAppRowsAddress`); `isAddressOf(resource, endPoint)`, which Table, Chart, Text and Form check, counts it only for a Database table, never as an address typed into another resource; `isModelsApiAddress` is not widened, so a page can't name another model's rows). `validateRow(schema, values, { partial })` types what a form sends (numbers as number inputs write them, `.5` or `1e3`, refusing whole numbers past 2^53; dates in any year; yes/no from text or 1/0; a number given for text or a choice as its text, as sample rows hold them), fills defaults on a new row, drops keys the table doesn't have (`id`, `created_at`, `updated_at`, `__proto__` included), caps text (`MAX_TEXT_LENGTH`, `MAX_LONG_TEXT_LENGTH`), and for a change checks only the fields given (emptying a required one is a problem, others are `cleared`). Row ids are ULIDs (`ulid(time, randomBytes)`, `isRowId`); a table's sample rows get fixed ids (`sampleRowId(i)`). **`RowStore`** (`src/rows.ts`) keeps rows per `TableRef` (`model`, `space`: `draft` or `live`, `table`), in the order added, each with `id`, `created_at`, `updated_at`, and `created_by` (the person signed in on the published app who added it, when one did): `list` (`createdBy` lists only theirs), `get`, `create(…, createdBy?)`, `update` and `delete` (which says whether it deleted), each with `OwnedBy` (`createdBy`: only a row that person added, checked in the same statement as the write), `update(…, changes, cleared)`, `delete`, `storeSampleRows` (once per table, even after its rows are deleted, and safe when asked twice at once), `keepTables` (drops the rows and sample marks of a space's other tables), `copySpace` (a model's space made a copy of another's, rows and sample marks, for a first publish), `countRows` (rows per table in a space), `rowsBy` (a person's rows by table, for their download), `forgetPerson` (a deleted account's rows deleted, or kept without `created_by` in the tables named; with `remember`, once the account is gone, the person is remembered as forgotten there, so `create` in their name afterwards throws `PersonForgottenError`, checked in the insert itself: a request that read their session before the deletion adds nothing; a 401 from the rows API) and `deleteModel`, with `MAX_TABLE_ROWS` (1,000) and `MAX_ROW_BYTES` (16 KB of JSON in UTF-8, `rowBytes`) as `RowLimitError`s. `MemoryRowStore` is the reference implementation, and every implementation passes `test/row-store-contract.ts` (`describeRowStore`). `HTTP_METHODS` includes PATCH.
- **Publishing** (`src/publish.ts`; the Data Apps slice, iteration 2, planned in the Modernization Plan doc): a model published as an app at `<slug>.apprun.app`. `slugProblem` says in words what keeps a slug from being an address (3 to 40 lowercase letters, digits and single hyphens, no hyphen at either end, so no punycode `xn--`; not in `RESERVED_SLUGS`, names that read as the site itself or that mail and network clients look up, such as `autodiscover`), and `suggestSlug(name)` makes a valid one from a model's name, cut after a whole word. `diffSchemas(published, draft)` (the published version's `databaseTables`, and the draft model) lists what a publish changes for the app's stored rows, in published order: a `removed-table` (whose live rows a publish deletes, after asking), and per field `removed-field`, `changed-type`, `newly-required` and `removed-options`; new tables, fields and options change nothing stored, and a draft table still in the model that doesn't generate is not removed (it keeps its rows, as on a save). `builderAddresses(model)` lists what only works in the builder, read from the generated document (so disabled features count for nothing): links and buttons to a path on the site other than the page itself (`/`, `/?…`, `/#…`), a Form's Then open, a table's `dataLink` template (`dataLink :/models/{id}`, in its columns or applied by position; a `dataLink :field` reads its address from the row), and data read from the models API. On an app's host every path shows the app again and the models API isn't served, so the Publish dialog warns about each. `schemaChangeText` and `builderAddressText` say each in words.
- **Illustrations** (`src/illustrations.ts`): the catalog of built-in illustrations (`banner/*`, `spot/*`, `divider/*`: id, name, default alt text, aspect ratio; `banner/map` is the Map feature's drawing, also offered to Images). The engine knows only names and shapes; the `illustration` node kind carries `{ name, alt, width, align, aspect? }` (empty alt = decorative). Banners take a Height (`BANNER_HEIGHT_SCALE`: short 6:1, medium 4:1, tall 16:5, or any % of the width from 10 to 60) as `aspect`, so the height follows the width. The web renderer draws them.
- **Sizes** (`src/sizes.ts`): heights chosen by name or as a number between (`HeightScale`: what short / medium / tall mean, the unit, `%` of the width or `px`, range and step; `readHeight` / `formatHeight` / `heightText`, stored as the name or `28%` / `260px`, so stored names stay valid), and widths in pixels or `full` (`readWidth` / `formatWidth` / `widthText` / `widthCss`; `MAX_WIDTH_SCALE` for a Container's Max width, `MIN_HEIGHT_SCALE` for its Min height (pixels only: a `PixelScale` without `full`), `CONTENT_WIDTH_SCALE` and `CONTENT_WIDTH_PRESETS` (Narrow 720, Standard 960, Wide 1120, Full) for content widths). `heightInput(name, scale)` declares a Height (`control: 'height'`, `heightScale`); pixel sizes use `control: 'pixels'` with a `pixelScale` and named sizes as `options`. A value neither reads is a warning and the default.
- **Golden tests:** `test/fixtures.test.ts` migrates `sample.json` and every `app_models/*.json`, then snapshots the v2 model summary, migration notes, document outline and diagnostics. Snapshot diffs are the review record. Read them before running `vitest -u`.
- **Storage:** `ModelStore` (`src/store.ts`) is the persistence interface for the browser store and the Worker (`D1ModelStore`). `MemoryModelStore` is the reference implementation. Models have revisions (how often they were saved; not the format `version`): `get` returns `{ model, revision }` (1 when created, one more per update), and `update(id, model, ifRevision?)` returns the new revision, throwing `ModelConflictError` (with the stored revision) when `ifRevision` isn't the stored one; without it, it overwrites. `list` gives `{ id, name, updatedAt }` (ISO 8601). Every implementation must pass `test/store-contract.ts` (`describeModelStore`), which `packages/web` also imports. The stores the Worker runs on (`D1ModelStore`, `MemoryModelStore`) are `ServerModelStore`s: `put(id, model)` also stores a model under an id of its choosing (creating it at revision 1, or replacing it like an update), for the home page; they pass `describeServerModelStore` too. `newModel(name)` (`src/edit.ts`) is a new model: one empty page.
- **Packaging:** source uses `.js` import specifiers so `tsc -p tsconfig.build.json` emits runnable ESM to `dist/`. `exports` has an `@feature-domain/source` condition (TS source, for Vite/Vitest via `resolve.conditions` / `customConditions`; deliberately not a generic `source`, which other packages also define) and a `default` condition (built `dist/`). `npm run smoke` proves plain Node can import it.

### `packages/worker`: the Cloudflare Worker (Hono, D1)
- **What it serves.** `wrangler.jsonc` (Worker name `app`, so its address is `app.feature-domain.workers.dev`; its Vite environment is `app`). Static assets are the web build (the `ASSETS` binding): unknown paths get `index.html` (client routes like `/models/:id`), and `html_handling: none` serves files at their own paths (`/preview.html`, no redirect). **Every request runs the Worker first** (`run_worker_first: true`), which picks the site by host (`src/hosts.ts`, `siteOf`): the **builder** at exactly `BUILDER_HOST` (`app.feature-domain.workers.dev`), a **published app** at `<slug>.APP_DOMAIN` (one label under `apprun.app`, the route `*.apprun.app/*`), and a plain 404 for any other host (the apps' apex, deeper names), so a wrong setting never serves the builder on an app's address. Both are vars in `wrangler.jsonc`; `.dev.vars` (committed, no secrets; wrangler never uploads it, though the build copies it to `dist/app`) sets both to `localhost` for `vite dev`, `vite preview` and the tests, so apps run at `<slug>.localhost:5173` (and the builder only at `localhost`: `127.0.0.1` or a LAN address gets the 404). `createApp(options)` (`AppOptions`: `store`, `upstream`, `rows`, `apps`, `hosts`, each defaulting to D1, the real fetch and the vars) returns `{ fetch, request }` (`request` as Hono's: a path is on `http://localhost`, the builder); the builder and the app host are separate Hono apps, each mounting its API with `mountApi` (`src/http.ts`: `API_HEADERS`, the `/api` 404 and the 500, which carries `API_HEADERS` or `PAGE_HEADERS` itself, for errors thrown before the API's header middleware runs). The builder passes non-API requests to `ASSETS`.
- **API** (`src/app.ts`, `createApp`): `/api/v1/models` list (`[{id, name, updated_at}]`, in creation order, leaving out the home model), POST (201 `{id}` + `Location`; a body that is only `{ name }`, as a form sends, starts `newModel(name)`, and an empty name is a 400), and `/:id` GET, PUT (204), DELETE (204; deleting a missing model is not an error); other methods get a 405 with `Allow`. A model's revision is its `ETag` (`"3"`; POST, GET and PUT send it): GET answers a matching `If-None-Match` with a 304, PUT with `If-Match` saves only over that revision (a 412 carrying the stored revision's ETag otherwise; `*` means any; a weak `W/"3"` counts as 3, since Cloudflare's edge weakens tags when it compresses; anything else is a 400), and PUT without it overwrites. Model reads are `Cache-Control: no-cache`. A missing model is a 404 (the Ruby app's 410 is gone). Models are checked with the engine's `validateModel` (400 with `problems`), sent as `application/json` (else 415), at most `MAX_MODEL_BYTES` (413), counting both the body and the stored row (the JSON plus the name, stored twice). **Local D1 doesn't enforce Cloudflare's limits** (2,000,000-byte rows, 100,000-byte statements), so tests check sizes themselves. Every `/api` response is JSON; errors are `{ error, problems? }`, and a 500 reveals nothing. **`POST /api/v1/proxy`** (`src/proxy.ts`) fetches an address for a page: `{ model, method, url, body?, requestType? }` (the web app's `DataRequest` plus the model id; JSON only, so a cross-site form can't send it). Never an open proxy: only http(s) addresses on the default port, no user name or password, no IP addresses, local names (`localhost`, single labels, `.local`, `.internal`, …), names ending in a dot or this site's host, or the platform's own hosts (the builder, the apps' domain and every app, `isPlatformHost`, so a page can't reach another app's rows through it), on an origin of the stored model's Server addresses (the engine's `proxyAddresses`, cached per model version in each app, `versionCache`, keyed `draft:<revision>` or `live:<version>`). The checks read the name, not where DNS points it: Cloudflare refuses subrequests to private addresses, but in local dev a public name resolving to one (e.g. `*.nip.io`) is fetched. It sends only its own `Accept` and `User-Agent` (no cookies or Access headers), the body as JSON, form-encoded or multipart, follows at most 3 redirects (each checked the same way; a 303, or a 301/302 after a POST, becomes a GET), gives up after 10 s (504) and refuses answers over 5 MB (502) or requests over 1 MB (413) (`PROXY_LIMITS`). It answers with the site's status, `Content-Type` and body only, marked `X-Proxy-Answer: site`; its own errors carry `X-Proxy-Error: true`. `AppOptions.upstream` is the fetch it uses (tests). `GET /api/v1/openapi.json` is the models API as an OpenAPI 3 spec (`src/openapi.ts`, `MODELS_API_SPEC`; its server is `/api/v1`, so its operations are paths on this site; a test checks it lists exactly the methods each route takes). **The home model** (`src/home.ts`: `HOME_ID` `home`, `homeModel()`) is the app's home page, built from features: a theme, an API spec feature storing `MODELS_API_SPEC`, a banner, a title and intro, a Form posting a name that opens `/models/{id}`, and a Table of the models (each name a `dataLink :/models/{id}`, the date it last changed, Delete). `POST /api/v1/home/reset` puts it back (`put`, 204 with its ETag; sent as `application/json`, else a 415, so a form on another site can't send it), over a broken one or in place of a deleted one. Every `/api` response also carries `API_HEADERS` (`Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `nosniff`, `no-referrer`), errors included.
- **Rows** (`src/rows.ts`, `mountRows`, registered by both sites): a Database table's rows at `/api/v1/models/:id/tables/:table/rows` (GET lists them as a plain array, POST adds one: 201 with the row and its `Location`) and `…/rows/:row` (GET, PATCH changes the fields sent, DELETE: 204, and deleting a missing row is not an error); other methods get a 405 with `Allow`. On the builder these are the draft's rows (`space: 'draft'`); a published app's are `live`. Each request reads the stored model and its Database tables (the engine's `databaseTables`, cached per model version like the proxy's origins, `versionCache`, which forgets a model when it is deleted, as one stored again under its id restarts at revision 1), so a field a save adds is taken at once; a missing model, a key that isn't a Database table of it, or a row id that isn't a ULID is a 404. The first request to a whole table (a list or an add; a request to one row needs an id it was given, so it skips the extra read) stores its sample rows (`storeSampleRows`). A save (PUT, or the home page's reset) deletes the draft rows of Database tables the model no longer holds (`keepTables` with the engine's `databaseTableKeys`, every Database table instance, generating or not), because the editor numbers a new feature after the highest id, so a new table can get a removed one's id and must start empty; the save has landed by then, so a failure there is only logged. Bodies are `application/json` only (415; so a form on another site can't send one), at most `MAX_ROW_REQUEST_BYTES` (413), checked with the engine's `validateRow` (400 with `problems`, in words); the server sets `id` and the times. A row past `MAX_ROW_BYTES` is a 413 and a table past `MAX_TABLE_ROWS` a 409. Reads are `Cache-Control: no-store`. `AppOptions.rows` is the row store (tests); without one, the routes use `D1RowStore` on the DB binding. Deleting a model deletes its rows and its app with its versions (`deleteModel`, after the model).
- **Publishing** (`src/apps.ts`, routes in `app.ts`; the Data Apps slice, iteration 2). `POST /api/v1/models/:id/publish` `{ slug?, copyDraftRows?, removeTables? }` (at most 16 KB, 413) makes the stored draft the app's next version: `If-Match` must name the revision being published (428 without one or with `*`, 400 for a tag it couldn't have sent, 412 with the stored ETag when the draft changed since: the editor saves first). The home model is never published (400: it is the builder's). A model generating with an error diagnostic is a 400 with `problems`. The slug is the request's, else the app's current one (400 without either; the engine's `slugProblem`, 400; another model's app has it: 409). Tables of the app the draft no longer holds (`databaseTableKeys`), the newest version's and any other the app still keeps rows in (`countRows`), must each be named in `removeTables`, else a 409 naming them; after publishing, their live rows go (`keepTables` on `live`, logged on failure, like a save's). One request at a time publishes or unpublishes a model (`withClaim`: `AppStore.claim` / `release`; another meanwhile is a 409 `The model's app is being changed`; a claim older than `PUBLISHING_CLAIM_MS`, a minute, is taken over, and the version is stored only while the claim holds, in the same transaction, else `ClaimLostError` and the same 409; the live rows' reset before it isn't fenced that way), so no publish acts on versions or live rows another is changing. Deleting a model doesn't wait: it deletes the app before and after the model, and a publish that finds its model gone once it stored a version takes it down (404). A first publish starts the live rows afresh *before* the app is served (so no visitor's row is lost to it, and a failure publishes nothing: trying again can still copy), then stores version 1 (`publish(…, { first: true })`, which throws `AlreadyPublishedError` when a version exists: a 409 `The model was published meanwhile`): `copyDraftRows` copies the draft's (`RowStore.copySpace`, sample marks included, so a deleted sample row doesn't come back), else none (each table starts with its sample rows); `copyDraftRows` on a later publish is a 400. It answers `{ slug, url, version, published_at }` (`url` from the builder's scheme and port, `appUrl`). `GET /api/v1/models/:id/publication` gives `{ published: { slug, url, version, published_at } | null, url_template (where an address name would put the app, `{slug}` standing for it), latest: { version, published_at, model } | null, live_rows: { <table key>: count } }` (no-store; every table a publish asks about removing: the newest version's and any other the app keeps rows in, counted in one query, `RowStore.countRows`) for the Publish dialog; `GET …/versions` lists the versions newest first (`[{ version, published_at, name }]`, no-store), `GET …/versions/:n` reads one (`{ version, published_at, model }`; 404 for none), and `POST …/versions/:n/publish` `{ slug?, removeTables? }` publishes it again as the next version (rolling back: versions never change, and the draft stays as it is), with the same checks and claim as a publish of the draft (both go through `release`, which generates it as the engine does now: an earlier version with an error diagnostic is a 400 too; `copyDraftRows` is a 400); `DELETE` unpublishes (204): the app goes offline and its slug is free, its versions and live rows stay, and publishing again counts on. **`AppStore`** (`claim`, `release`, `publication`, `versions` (newest first, without their models; D1 reads the name with `json_extract`), `bySlug` (the model and version number only: every request to an app asks), `version` (one version's model), `latest`, `publish` (throws `SlugTakenError`, and with `first`, `AlreadyPublishedError` when a version exists), `unpublish`, `deleteModel`): `MemoryAppStore` is the reference, `D1AppStore` runs on migration 0004 (`versions(model_id, number, model, published_at)`, the model JSON without its id; `apps(model_id PK, slug UNIQUE, version, published_at)`; claims in `publishing(model_id PK, token, since)`, migration 0005, one upsert taking a free or stale claim, and each of a publish's writes conditional on it; a publish is one batch: the next version, then the app updated or inserted, so a taken slug fails the UNIQUE constraint and stores nothing), and both pass `test/app-store-contract.ts` (`describeAppStore`).
- **A published app's site** (`src/appHost.ts`, `createAppHost`): outside development (the apps' domain isn't `localhost`) it is https only: plain http gets a 308 to the same address over https, and every answer carries HSTS (`APP_HSTS`, a year, subdomains included, not preloaded; the zone's Always Use HTTPS stays off, as its 301 would turn a POST into a GET); the model is always the one the host's slug names (`bySlug`), never one a request names. Each request reads only the slug's model id and version number; the version's model is read for `/api/v1/app`, or when its tables or proxy origins aren't in `versionCache` yet (under `live:<version>`, `load`), and isn't kept itself (models can be large). A model's version number is never used twice (no publish is undone, and model ids are random UUIDs; the home model is never published), so what is cached under it, in any isolate, and the ETag stay right. Deleting a model deletes its app first (and again last, see Publishing), so a failure later never leaves an app serving a model that is gone. `GET /api/v1/app` is the published version (its number and the model's id the ETag, `"3.<id>"`, since an address can pass to another model's app; 304 on `If-None-Match`, no-cache); `/api/v1/app/tables/:table/rows[/:row]` the live rows, checked against the published version's tables (a draft's newer table is a 404); `POST /api/v1/app/proxy` the proxy for the published version's Server addresses (`{ method, url, body?, requestType? }`: a `model` in it is a 400, `readProxyRequest(…, { model: false })`). Nothing is published there: every `/api` request is a 404 `No app is published at this address`. Nothing of the builder's API answers on an app's host (its `/api` 404). A request for a file (`Sec-Fetch-Dest` other than a document or a fetch's `empty`, so Vite's modules in development too, or a path under `/assets/`) goes to the assets, where an HTML answer (the single-page fallback, i.e. a missing file, or the editor's own pages) is a 404, never the editor's page; a path with an extension from a fetch or a client that doesn't send it is tried as a file, and is the app's page when the assets answer HTML. Every other GET or HEAD is `app.html` (asked for as a page), with a 404 where nothing is published (`no-store`, without the page's `ETag`, so a browser's revalidation once an app is published there can't keep the 404); other methods 405. The builder's and app's proxies share `answerProxy` (`src/proxy.ts`).
- **Sign-in tables** (`src/auth/`; the Data Apps slice, iteration 3, planned in the Modernization Plan doc; the spike's findings in `spike/FINDINGS.md`). A published app whose version has sign-in (`hasSignIn`: a Sign-in feature that generates, the engine's `signInOf`) gets Better Auth tables of its own in the one D1 database: `app_<key>_user`, `_session`, `_account`, `_verification`, `_rate_limit`, named after a random 32-hex key kept in `app_auth(model_id, key, schema_version)` (migration 0006), never after the model id (samples' ids are `sample-2-6`) or anything a request names (`authTables(key)` refuses anything else). Their schema is `AUTH_SCHEMA_STEPS`, add-only steps (step 1 is what Better Auth 1.7.14, pinned exactly, creates; `test/authSchema.test.ts` asks Better Auth's own `getMigrations` what is missing, so an upgrade adding a column fails CI). `D1AuthTables` (an `AuthTables`; `MemoryAuthTables` keeps only the record, for the web tests' in-process API) `ensure`s an app's tables (created, or the missing steps applied; never dropped) and `drop`s them, each one app per D1 batch: a batch is one transaction, DDL included, so of two requests making the same change one rolls back and reads the result, and an upgrade's record goes first with a `changes() = 0` guard so it applies nothing to an app dropped meanwhile; only a change another request made is retried. Never several apps per batch: schema changes slow down as tables pile up (on Cloudflare's D1 one `ALTER` takes 177 ms at 1,000 apps, 1 s at 3,000, holding up every write meanwhile; 50 `DROP TABLE`s in one batch at 3,000 apps hit D1's CPU limit), hence a cap of 1,000 apps with sign-in (proposed). Every publish of a version with sign-in ensures the tables before the app is served (rollbacks too); deleting a model drops them last (only logged on failure), and so does a publish finding its model deleted meanwhile, on success or failure. `upgradeAll` (`npm run db:upgrade-apps`, through `getPlatformProxy`; `-- --remote` writes a config marking the DB binding remote) upgrades outdated apps, drops deleted models' tables and sweeps tables no `app_auth` row names. `authConfig` / `authFor` (`src/auth/authFor.ts`) are an app's Better Auth: its tables, a secret derived per app (`appSecret`, HKDF of the platform secret and the key; one shared secret would let a cached session cookie pass on another app), its exact address, `validateSchema: false` (else every new instance reads the whole database's schema), the email-code plugin (the email's button link carries the code after `#`), `ctx.waitUntil` for background work, `cf-connecting-ip`, rate limits in the app's table, and `__Host-fd.*` cookies on https; the email names the app (`appName`), `signUp: false` answers an unknown address as a known one and sends it nothing, and `allows(email)` (listed emails and domains) sends nothing to an address it refuses, with the same answer; `user.deleteUser` is on; the database rate limiter skips `/get-session` and `/sign-out`.
- **Sign-in on an app's host** (`src/auth/route.ts`, `mountSignIn`, registered by `createAppHost`): `/api/v1/app/auth/*` is Better Auth for the app the host names, built per request (`authFor`), only while its published version has sign-in (`appSignIn`: the Sign-in feature's settings and the app's name, cached per version as `signInOf`, like its tables) and it has auth tables (outdated ones are brought up to date first: the lazy upgrade; a version with sign-in but no tables, a publish that failed at that step, is a 503 of its own). Only `AUTH_ENDPOINTS` answer (get-session, sign-out, send-verification-otp for type `sign-in` only, sign-in/email-otp, delete-user; anything else a 404, a wrong method a 405), bodies at most `MAX_AUTH_REQUEST_BYTES`. Changes (every method but GET) must come from the app's own origin (`Origin`, else 403) as `application/json` (else 415): Better Auth checks the Origin only once a cookie is sent, and reads form bodies, so this stops login CSRF. Answers drop the session token from their JSON (`withoutTokens`: it lives only in the HttpOnly cookie) and are `no-store`. `GET /api/v1/app/account` downloads what the app holds about the person signed in (account, sessions and the rows they added, by table name, no tokens; 401 when signed out; only from the app's own page: a `Sec-Fetch-Site` other than `same-origin` or `none` is a 403). Deleting an account forgets their rows before it (`forgetUser`, Better Auth's `beforeDelete`: `RowStore.forgetPerson` with the tables set to keep them; a failure there keeps the account to try again) and again once it is gone (`afterDelete`, with `remember`, so a deletion that fails locks no one out). **Table rules** on an app's live rows (`allowed` in `src/rows.ts`, with `RowsTarget.visitor`, which only the app host sets): `visitorsOnly` also reads the session wherever the table's rule needs to know who asks (`visitor(c, wants)`, `wants` worked out only for an app open to anyone, as it may read the version's tables: `needed` by the engine's `operationNeedsPerson`, which counts the See rule for a change or delete, as `rulesFor` says and `writer` checks), and when a row is added with a session cookie sent (`'wanted'`: it records `created_by`; a sign-in that can't be checked then refuses nothing), even in an app open to anyone; a rule needing someone signed in is a 401 for no one (`Sign in to … this table's rows`), a 403 in an app without sign-in, nobody a 403; Owner lists only the person's rows (`list` with `createdBy`); a change or delete also needs the right to see the row (`writer`), under Owner (or where people see only their own) the write itself checks who added it, and another's row is then a 404 where they can't see it, else a 403 (`Only the person who added a row can …`); a row no one added (sample rows, rows added signed out) is no one's under Owner; rules are checked before sample rows are stored. Pages never get `created_by` (`pageRow`). The session cookie cache stays off: a session read is a fast D1 read, and the cache would let a deleted account's other sessions go on working for its lifetime. **Who can open the app** is enforced by `mountSignIn`'s `visitor` gate on `/api/v1/app`, its rows and its proxy (sign-in itself stays open): for an app open to signed-in or listed people, no session is a 401 and a session whose email the list no longer holds a 403, each `{ error, sign_in: { app, theme?, email? } }` (`SignInAnswer`, no-store; `theme`: the app's first page's, for its sign-in page), which the app's page (`loadPublishedApp`, status `sign-in`) tells from an expired Access session; what it lets a signed-in person see is `private` and `Vary: Cookie`, and a session the read extends sends its renewed cookie; a method the route doesn't take is still its 405; an app that needs sign-in but can't check it (no secret, no tables) lets no one in (503). No published version, or no sign-in, is a 404; no `AUTH_SECRET` (a Worker secret; `.dev.vars` has a development-only one) a 503, and no mailer when a code is asked for a 503. Codes go through `Mailer` (`src/auth/mailer.ts`): in development (the apps' domain is localhost) `DevMailer`, which prints each email to the Worker's log and keeps the last ones, which `GET /api/v1/app/dev/mail?to=` serves only there (for `e2e/signIn.spec.ts`); otherwise `CloudflareMailer` on the `EMAIL` binding (Cloudflare Email Sending, `send_email` in wrangler.jsonc, allowed to send only from `MAIL_FROM`, `sign-in@apprun.app`), under the app's name, sent through `ctx.waitUntil`; `AppOptions.mailer` swaps in `MemoryMailer` (tests). infrastructure/README.md has the one-time setup (the secret, onboarding apprun.app for Email Sending).
- **Storage** (`src/d1ModelStore.ts`, `src/d1RowStore.ts`, `src/d1AppStore.ts`): `D1ModelStore` implements `ServerModelStore` on `migrations/` (`models(id, name, model, created_at, updated_at, revision)`, `settings(key, value)`; one `UPDATE … AND revision = ? RETURNING revision` checks and writes; `test/migrations.test.ts` checks each migration on rows stored before it, so no save lands in between); the JSON leaves out the model's id (the row's id is put back on read); `list()` orders by `created_at, rowid`, its times from `updated_at` (ms); `put` is one `INSERT … ON CONFLICT (id) DO UPDATE … RETURNING revision` that keeps `created_at`. (`@cloudflare/vitest-pool-workers` needs Vitest 4, so it isn't used.)
- **Deploying** (`infrastructure/`, its README has the steps): a Cloudflare account of its own, on `app.feature-domain.workers.dev`. Terraform (state in R2) owns what outlives a deploy: the D1 database and Cloudflare Access (its session cookie `SameSite=Lax`; an email allow list; sign-in by one-time code or Cloudflare login) in front of the whole hostname, editor and `/api` alike; and for published apps, the `apprun.app` zone (registered with Cloudflare Registrar in this account; looked up, not managed): a proxied wildcard record `*.apprun.app` (`AAAA 100::`, since a Workers route needs a proxied hostname and Custom Domains don't take wildcards; the apex has none) and an Access application on `*.apprun.app` with the editor's allow policy, until apps have sign-in of their own. ### `packages/web`: the Vue app (Vite, Vue 3, Pinia, vue-router, Tailwind v4)
- **The Worker in Vite.** `vite.config.ts` loads the Cloudflare Vite plugin with `packages/worker/wrangler.jsonc` (left out under Vitest), so `vite dev` and `vite preview` serve `/api` from the Worker in workerd, and `vite build` emits `dist/client` (the app) and `dist/app` (the Worker and its generated `wrangler.json`). The two-page input is set on the `client` environment only, and the Worker's environment gets the `@feature-domain/source` condition too. Its D1 data is the worker package's; `FD_STATE_DIR` points elsewhere (the e2e tests use a fresh `.wrangler/e2e-state`).
- **Routes** (`src/router.ts`): `/` is the home page (`HomeView`), `/models` the built-in model list (`ModelListView`), `/models/:id` the editor. `HomeView` reads the home model (`HOME_ID`) and renders it as the preview would, under a `SiteHeader` with **All models** and **Edit home page** (outside the generated page, so no edit removes the way back). When the model is missing, invalid, generates with an error diagnostic or shows no page, the built-in list (`components/ModelList.vue`) takes its place with a notice and **Reset home page** (`homeReset()` in `src/services.ts`, `ApiModelStore.resetHome`; asked first in an in-page dialog unless the home page is missing); a failed load offers Try again instead.

Its **sign-in page** (`signInDocument`, rendered by `DocumentView` in the app's theme; `nodes/SignInNode.vue`) shows where the app asks for sign-in (status `sign-in`; for someone the list leaves out, Sign out first) and at `/sign-in` for an app with sign-in (the Account's button and the emailed link, `?email=…#code=…`, whose code it fills in, drops from the address and still waits for a press): an email, then the six-digit code, with what went wrong in words and a privacy line; signing in reads the app again (from `/sign-in`, opens `/`). `src/renderer/account.ts` calls the app's sign-in endpoints with fetch (no client library). The **Account** (`nodes/AccountNode.vue`): in the builder the signed-out look, doing nothing; on an app (`DataStore.onApp`) Sign in (a link to `/sign-in`), or who is signed in with Sign out, Download my data (`/api/v1/app/account`, fetched, so a session that ended meanwhile is said rather than saved as the file) and Delete my account (asked inline, focus following); nothing on an app without sign-in; Try again when it couldn't check. - **Content Security Policy.** `public/_headers` gives every page and asset a CSP (scripts, styles and fonts from this site only; images from any https address or `data:`; fetches to any https address, since data resources fetch from the browser; no objects, base, form actions or framing), `nosniff` and `no-referrer`. `vite preview` applies it, and Cloudflare does to assets it serves itself; but the Worker runs first and passes every page and file on, and Cloudflare doesn't apply the file to Worker answers, so the Worker sets the same headers itself (`PAGE_HEADERS`, `withPageHeaders` in packages/worker/src/http.ts; a Worker test checks they match this file). Under `vite dev` (`import.meta.hot` is set, which every build leaves undefined, whatever its mode; `pageHeaders`) it leaves the CSP off, since Vite injects styles inline. HTML pages carry no inline `<script>` or `<style>` (the preview's base styles are `src/preview.css`). `style-src` has no `'unsafe-inline'`, so `vueCompilerOptions.ts` (used by `vite.config.ts`) turns off Vue's static hoisting (`hoistStatic: false`), which would turn large static templates such as the illustrations into HTML strings whose style attributes the policy refuses. Style bindings set through the DOM are allowed. `isolateNetwork` fails any e2e test that logs a CSP violation (`isCspViolation`; `e2e/api.spec.ts` checks that an injected script is refused and reported that way, so the guard can't go blind), and checks the headers on pages and every kind of asset. `test/csp.test.ts` checks the compiler options still keep illustrations from becoming HTML strings. `Permissions-Policy` turns off camera, microphone and location, and `Cross-Origin-Opener-Policy: same-origin` isolates the windows.
- **Rendering.** `src/renderer/` renders a `DocNode` tree. `NodeView` picks a component per node kind from `nodeComponents.ts`, which is typed as a full `Record<NodeKind, Component>`, so a new kind fails the typecheck until it has a component.

- **Generated-page styling.** `document.css` is plain CSS driven by the theme. The legacy Bootstrap look is gone.
  - **Themes** (`packages/engine/src/theme/`): `deriveTokens(params)` turns theme settings (accent, band color, light/dark scheme, font pairing, base size, scale ratio, radius, density, shadow) into `--fd-*` custom properties. Colors are computed in OKLCH with gamut mapping, and `ensureContrast` moves each text color's lightness until it reaches 4.5:1 against every surface it can sit on. It also derives six chart colors (`--fd-chart-<n>`, `CHART_COLORS`): the accent, then hues a sixth of a turn apart ordered so neighbors are a third apart, alternating lighter and darker, each at least 3:1 against the page and cards; and a band set (`--fd-band-chart-<n>`, 3:1 against the band and its raised cards), which a band well re-points `--fd-chart-<n>` to. Seeded property tests cover contrast, lightness order, badge hue separation, chart colors and determinism. `clampThemeParams` turns any stored values into valid settings.

The element carrying a theme (`[data-fd-scheme]`: the root now, pages later) provides it (`renderer/theme.ts`, provide/inject), and each component puts its choice on its **own** element as `data-fd-<component>`, so a nested theme wins over an outer one. `document.css` has one rule block per option, keyed to the component's own attribute (never an ancestor's). `deriveTokens` also returns `adjustments`: colors it changed for readability, in words, for the editor to show. A web test fails if any option lacks rules, if `document.css` uses a `var(--fd-*)` the engine doesn't emit, or if a font pairing names a web font that isn't bundled. A `band` well re-points the color tokens to the band set, so content inside stays readable.

A built-in theme is only a set of settings; tests check each derives with no readability adjustments. `themeInputs(params)` / `themeParams(inputs)` convert between settings and a Theme's inputs, and `matchingPreset(inputs)` names the built-in theme a Theme matches exactly.

A Page's `theme` input is a **soft reference** to it: the page carries the tokens as `props.theme`, and `PageNode` applies them and provides the theme to the components inside. Pages are full width (side padding keeps content within the theme's Content width, `--fd-content-width`: 1120 px by default, the `contentWidth` setting, or `100%` for full; a page's own Content width overrides it), so a themed page paints edge to edge.

  - **Except shapes inside an `<svg>`:** their geometry and paint (`r`, `d`, `fill`, …) are CSS properties set by presentation attributes, so a revert would erase the drawing. `:where(.fd-root *:not(svg *))` gets `all: revert`; SVG internals revert only the box properties editor base styles set on every element (border, outline, box-sizing, margin, padding). The e2e isolation test catches anything else that leaks.

Banners are two stacked SVGs, so they suit any height: a background that fills the frame (`slice`) and a drawing that always fits whole (`meet`). Tests check each has no scripts, handlers or external references, uses only tokens the engine emits, and hard-codes no colors. Never load illustration images from other sites.
  - An e2e test renders the preview's document at exactly the editor canvas's width, then compares *every* computed property of every element in the editor and the preview, except a short list of layout-dependent ones, including with leaky utility classes added to the canvas wrapper. It fails if the isolation breaks.

  - Containers and card panels with nothing in them (e.g. holding only disabled features or ones of an unknown type) add no margin or empty card (`:empty` / `:has`); in the editor their slots still get drop areas, and empty containers keep their margin (`main.css`).

URL policies are in `renderer/urls.ts` (the CSP narrows them further: on the https site browsers upgrade `http:` images and refuse `http:` fetches as mixed content, and under `vite preview`, served over http, the policy refuses `http:` images and fetches): data fetches are http(s), or the models API on this site (the engine's `isModelsApiAddress`: `/api/v1/models`, or one model under it, with an optional query; never `.`, `..` or an encoded dot as a segment; so a page can't call the proxy or any other endpoint with the viewer's session; and every fetch or send to an http(s) address goes without cookies (`credentials: 'omit'`), so a full address on this site can't either); links are http(s) (a new tab) or a path on this site (the same tab; `safeHref`, `opensNewTab`); image sources are http(s), relative or `data:image/`.
- **Database table rows** (`renderer/data.ts`): the data store reads a `DataSite` (`{ model, app? }`) and resolves a Database table's relative address (`tables/2/rows`) to its own model's (`modelRowsAddress`), or on a published app's page (`app`) to the app's live rows (`appRowsAddress`), before fetching or sending, so a page reaches only its own rows (a store without a site says the rows need a saved model), and the browser fetchers accept only the current host's forms on this site, with the viewer's session: on the builder's site the models API and model rows (`isModelRowsAddress`), on an app's page (which calls `servePublishedApp` at start) only the app's rows (`isAppRowsAddress`). A browser fetch or send that fails outright (what CORS looks like) suggests switching to Server. The proxy reads the stored model, so in the editor `ModelView` provides `PROXY_READY` (`store.flush()`): requests through it wait for the pending save (and are refused while it can't be saved), and so does the API spec's Load spec with Server. The Data Resource's address is committed when the field is left (or on Enter), so a partial one is never fetched. The canvas still never sends.
- **Runtime data** (`renderer/data.ts`): each document has one `DataStore` (provided by `DocumentView`, given the model id). Readers of the same address share one fetch (`FETCH_JSON`, injectable): tables and charts read rows (`rows(source)`, each taking its own `path`; `reload(source)` refreshes them all), and a Text's values read a source's whole answer (`answer(source)`: the JSON at its address, or sample rows with added ones; it registers as a reader of the resource, so a Form's send reloads it too; "…" while loading; a value the answer doesn't have, or that couldn't be loaded, shows "—" on the page and its marked `{{binding}}` on the editor canvas, whose title says which (`store.live` tells them apart); an empty value shows empty; screen readers hear words instead of the marks), and a Weather card reads the whole response (`json(endPoint)`, as a `FetchState`, parsed by `renderer/weather.ts`; `refetch(endPoint)` for Try again). A stale response is discarded. A failed address is tried again when a new reader arrives, and an address with no readers left is dropped (so typing a URL keeps nothing). A source with `rows` (sample data) fetches nothing: it shows its rows plus rows added since (by a Form; capped at `MAX_SAMPLE_ROWS`), kept per model in `localStorage` (`feature-domain:sample-rows:<model id>`, ignored if unreadable, forgotten when the model is deleted). `send(action, values, fields)` (a Form; returns what was created: the added row, or the site's answer) and `delete(action, row)` (a table row) change data: on sample data they add or remove added rows (an added row without an id gets the next one after the sample's, as a server would: `sampleIds` on the action, text or number like the sample's; the last id given is stored too, so a deleted row's id is never reused); otherwise they go through `SEND_REQUEST` (injectable, http(s) only), path fields filling `{name}` placeholders (`fillPath`, which refuses `.` and `..`), query fields added, the rest as the body, then `reloadResource` refetches every address that resource is read through. `follow()` picks up rows added in another tab (the preview follows the editor). On the editor canvas (`DocumentView`'s `editing`, so the store isn't `live`) forms and row deletes change sample data but never send to an address: they throw `NotSentFromEditor`, which says to open the preview. Table fields read a key the row has as a whole (e.g. `first.name`) before reading it as a dotted path; a leading `data.` (the legacy row name) is dropped only when the full path finds nothing.

Loading, error with Try again, and empty states as tables.

While sent the select is `aria-busy` (never disabled, which would drop focus), each cell on its own, so other rows can change meanwhile (a second change of a busy cell is put back); afterwards it shows what is stored (Vue writes a bound value only when it changes); a failed change goes back, with an alert; on the editor canvas nothing is sent (`NotSentFromEditor`). A value the options don't hold shows as a disabled option.

Delete / Keep), never a browser dialog. Keyboard focus follows: to the question's Delete, back after Keep, to the next row's Delete (else the table) after deleting.

With Then open, a sent form opens the filled address in this tab (`OPEN_ADDRESS`, injectable) without waiting for the resource's readers to reload (`send`'s `waitForReload`), and can't send again while the next page loads (until the browser shows it again from its cache); the editor canvas only says what the preview would open, and an address nothing fills is said too.

Cells use a small filter language (`renderer/filters.ts`: `uppercase`, `lowercase`, `date`, `number` (every decimal, or `number :2` for fixed places; text must be a plain decimal and keeps every digit), `currency` (US dollars, or `currency :EUR`; same number rules), `badge`, `dataLink :path`, or `dataLink :/models/{id}`, an address whose `{path}` placeholders are filled from the row, each value encoded as one part of the address (`fillLink`; text, numbers and booleans only), no link when one is missing or is `.` / `..`); paths read only a row's own keys, and links are only ever http(s) or paths on this site.
  - A scrolling table shows exactly its Scroll after rows: the scroll box's max-height is set from the rows as they render (`renderer/tableFit.ts`, `scrollFit`: the bottom of the last row shown, `none` when every row fits), and document.css's estimate (2.75em a row) applies only until rows are loaded.
  - A table is a card: an optional Title with the row count (else the count in a footer), labels in the body font on a tinted band that is sticky while rows scroll ("Scroll after (rows)": stored tables without it show every row, new ones scroll after 10; the scroll box is a focusable, named region only while it actually overflows, measured with a ResizeObserver), dense rows with a hover highlight, stripes only for the theme's `striped` style.
  - Figures (`number` / `date` filters, or columns whose loaded values are all numbers) are right-aligned with tabular digits. Badges take the theme's four badge tints (`--fd-badge-<n>`, hues a quarter-turn apart from the accent, contrast-checked), given out per column in order of first appearance.
  - Loading shows skeleton rows under the real header; empty shows the `spot/empty` illustration; an error names the host and offers Try again.
  - A card Panel holding only a table lets the table be the card (`:has`). At phone width (`@container`, 520px) rows become cards with label/value pairs and no inner scroll box.

Below `lg` the columns stack.

A double-click, or Enter on a selected feature (its first marked text; from the page, nothing focused, or its tree row), makes the element `contenteditable="plaintext-only"` (browsers without it get a plain-text paste handler). The Enter confirming an input method's candidate is ignored. Enter or leaving commits through `store.editText` as one undo step; in a list or paragraphs Enter also adds `NEW_TEXT` after it and edits that (Shift+Enter only commits), and Escape on such an added entry takes it back out (`store.retract`, no redo step). Escape cancels. Before committing, the element's own rendered nodes are put back, so Vue re-renders it normally; any other regeneration ends the edit first (a pre-flush watch), and an edit that starts right after a change waits for the re-render. While editing, the feature isn't draggable (its and its ancestors' `draggable` are turned off, and `canDrag` checks `inlineEdit`), and the selection outline (amber) marks the edited text. Publishing saves first (`flush`), then publishes the revision saved (`savedRevision`, `If-Match`), and reads the publication again. The dialog: the address name (the app's, else `suggestSlug` of the model's name; `slugProblem` as it is typed; the address from `url_template`; a new name warns that the old address stops working), the draft's errors (Publish waits for them to be fixed), each table the draft removes as a checkbox naming the app's row count there (every table in `live_rows` the draft no longer holds, as the Worker works it out; all must be ticked), the other `diffSchemas` changes and `builderAddresses` in words, on a first publish whether the app starts with the draft's rows (off), and Unpublish asked inside the dialog (an in-page AlertDialog would open beneath a modal one). It works these out only while open. Its **Versions** list (newest first, the live one marked) offers Publish again… on the others: choosing one reads that version and checks it in place of the draft (its errors as the engine generates it now, its removed tables and changes against the newest version), until Publish the draft instead; Publish waits while a version is read, a read still going when a newer choice is made (the dialog opening again, another version, Publish the draft instead) is ignored, and the list is read again after each publish.
  - **Editing.** All edits go through `useDocumentStore` (`add`, `setInputs`, `editText`, `moveTo`, `remove`, `rename`), which applies pure engine operations, regenerates with placeholders, and autosaves 400 ms after the last change. **Saves go one at a time**, each sent with the revision the last one returned (`If-Match`), so a save is refused only when someone else saved in between, never by an earlier save from here; one ending after another model opened, or after `discard()`, is ignored. A refused save holds every later one (`saveState` `conflict`, or `deleted` for a 404) until the user picks **Load their version** (`loadTheirs`, which drops the edits and undo history) or **Keep mine** (`keepMine`, saving over the revision the 412 named), or **Save as a new model** (`saveCopy`); a failed save offers **Try again** (`retry`). The banner sits under the top bar (`save-problem`). On page hide the pending save goes out with `keepalive` (bodies under `KEEPALIVE_MAX_BYTES`, as browsers cap them at 64 KiB); `beforeunload` asks only when edits would be lost (`unsavedOnLeave`: a failed or held save, one queued behind another, or one too large for keepalive). Leaving within the app after a failed save asks before dropping the changes. **Saves made elsewhere** reach an open model through `useModelUpdates` (`stores/modelUpdates.ts`): this browser's other tabs hear of each save at once (`announceSaved` on a `BroadcastChannel`, `stores/modelChannel.ts`; messages carry a per-tab id, since every channel object in the saving tab hears them too), and every tab checks when shown again and every `CHECK_INTERVAL_MS` (10 s) while visible. Each check is a plain `get`: the browser revalidates its cached copy with the ETag, so an unchanged model costs a 304 (Playwright's routing turns the HTTP cache off, so e2e tests check the 304s at the API level). `refresh()` replaces the model only for a newer revision (a slow read can return an older one than a save that landed meanwhile) while nothing here is waiting to be saved and no text is being typed in place (the editor passes `inlineEdit`), ends undo history there, and shows a model deleted elsewhere as missing. Requests time out after `REQUEST_TIMEOUT_MS`, so a hung save becomes a failed one. An expired Access session gets its own banner: Sign in again (a new tab renews the session) and Try again, since reloading would lose the edits. When only the automatic upgrade on load is refused (another tab saved first), the editor quietly shows the stored model instead of a conflict. The editor and the preview both use it.
- **Drag-and-drop** (Pragmatic drag and drop):
  - `editor/dnd.ts` is pure and unit-tested. A drop zone is either an empty slot (append) or a feature (before, after, or "combine" = into its first slot). `evaluateDrop` maps the zone to a `PlacementTarget` and checks it with the engine's `canPlace`, detecting drops that change nothing.
  - `editor/useEditorDnd.ts` registers draggables and drop targets on the canvas (`[data-feature-id]`, `[data-slot]`), the tree (`[data-tree-id]`) and the palette (`[data-palette-type]`), rebuilding them after each regeneration and whenever collapsing or expanding re-creates tree rows (it watches `collapsedRows`). Anything else that re-creates draggable elements without a regeneration must trigger a re-registration too. It has one monitor that applies drops through the store (`moveTo` / `addAt`), so drops are validated and undoable.
  - Drop feedback lives in `editor/dndState.ts`, drawn by `DropIndicator` (canvas overlay, outside `.fd-root`) and `TreeRow`.

  - Empty slots get a drop area in the editor only (`main.css`, `.fd-editor-canvas`).
  - Draggability is decided by feature type, so unplaced features can be dragged from the tree onto the page.
  - Before or after a Page (the document root) is offered only when dragging a Page; anything else dropped at a page's edge goes into it.
  - Links and images inside a feature are extra drag handles for that feature. A press in a form field or button never starts a feature drag (`canDrag`), and form fields keep mouse text selection (`document.css`).
- **Undo/redo.** The store records history at its single `apply()` point, with the selection. Consecutive edits of the same input (or the model name) within 1 s are one step, capped at 100 steps. Loading and the automatic upgrade are not undoable. Buttons, plus ⌘Z / ⇧⌘Z / Ctrl+Y, except in text-entry fields (selects and checkboxes do use them) and while a confirmation dialog is open. Deleting a model discards any pending save first (`store.discard()`), then goes to the home page. The inspector's Move up / Move down and Location select are the keyboard alternatives to dragging.

## Architecture

### Server (Ruby/Sinatra)
- `config.ru` → `app.rb` (`App < Sinatra::Base`, modular style). `load_path.rb` puts `lib/` and the repo root on `$LOAD_PATH`.
- `app.rb` declares the asset bundles (sinatra-assetpack serves `app/js`, `app/css` and `app/images`, and compiles `.coffee` on the fly). **The JS bundle order matters**: vendor libs, then `application.js`, then `/js/*.js` alphabetically.
- Routes:
  - `GET /`, `GET /models/:id`: designer UI (`views/layout.slim` + `views/index.slim`, `designMode = true`).
  - `GET /models/:id/preview`: rendered app only (`views/content.slim`, no layout, `designMode = false`).
  - `/api/v1/models[/:id]`: REST CRUD on application models. GET on a missing id returns **410**, not 404. If the store is empty, `GET /api/v1/models` seeds it from `sample.json`.
  - `/api/app_features`: legacy endpoint that reads and overwrites `sample.json` on disk.
- `lib/model_access.rb`: models are stored as JSON strings in one Redis hash (`content_models`), keyed by UUID. The Redis client is created at class-load time (`Client` constant).
- `lib/redis_connection.rb`: reads credentials from `VCAP_SERVICES` (Cloud Foundry) with a fallback to `localhost:6379`.

### Client (CoffeeScript + AngularJS 1.3, `app/js/`)
- `application.coffee`: Angular module `sampleDomainApp`.
- `features.coffee` (~2000 lines, the core): `BaseFeature` plus ~20 `*Feature` classes, registered in the `FeatureClasses` map at the bottom. Each feature declares `name`, `icon`, an `inputs` schema (each input's `control` names a form directive in `form_directives.coffee`), optionally `visual_editor`, and a `generate(appMetadata, instance, inputs)` function. That function **mutates the DOM directly with jQuery** (appends into its target container) and returns `false` if its target doesn't exist yet. **To add a feature**: add a class and register it in `FeatureClasses`.
- `generator.coffee` (`AppGenerate`): runs every non-disabled feature instance in order and retries features that returned `false` (up to ~4 passes) so children can render after their containers. `generateInstance` does partial regeneration of one feature plus its dependents.
- `metadata.coffee` (`AppMetadata`): transient tree (tree-model.js) rebuilt on every generate. It records Pages → Targets, Features, DataResources (+ Operations), DataSchemas and feature dependencies. Features use it to discover each other, and editors use it to populate selectors (e.g. page targets, resources).
- `app_features.coffee` (`AppFeatures`): the loaded model's feature-instance list (add/move/delete/save via `$resource`).
- `controllers.coffee` (`ModelCtrl` load/save/saveAs/delete/preview, `FeaturesCtrl` drag-drop), `directives.coffee` (palette, feature list, editor, `generatedContent`, metadata view), `runtime.coffee` (`DataResource` service plus `serviceResource`/`googleChart` directives used by generated pages), `visual_editors.coffee` (inline contenteditable editing).
- Components communicate mostly through `$rootScope.$broadcast` events: `generateContent`, `featureSelected`, `featureUpdated`, `addFeature`, `moveFeature`, `postGenerate`, `deleteResource`, `postResource`.
- Generated HTML is `$compile`d by Angular after generation, so features can emit Angular directives in their markup.

### Data
- `sample.json`: seed feature list. `app_models/*.json`: example application models (Google Map, Swagger, "Buy Deal"; the Watson sample was removed when its feature was dropped). The new app no longer seeds these: they are the engine's migration fixtures.
- Feature instance shape: `{feature: "TextFeature", id: "27", inputs: {..., page_location: {name, target}}, cache: {}}`. `page_location.target` is a CSS selector (`#content_section`, `#page_container`, or a container cell id), which is how nesting works.

## Gotchas
- Instance ids are stringified integers (`AppFeatures.nextIndex`). DOM ids are derived as `<name>_<id>`, lowercased, with spaces replaced by underscores (`BaseFeature.instanceId`).
- Several inputs misspell `default` as `defaut` (e.g. the `disable` input), so they default to `''`. Specs depend on that behavior.
- `ScriptTestFeature` `eval`s a script built from user input. Persisted models can contain Angular `$$hashKey` fields.
- `rake package:build` just zips `app/`.
